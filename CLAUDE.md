# CLAUDE.md

Bro is the agent system: independent specialised agents (a "Bro") each run as a stateless LLM loop with their own system prompt and MCP-tool access. Conceptual model and rationale: `DESIGN.md`. This file maps the framework; `bro-dev/CLAUDE.md` maps the development tooling that ships beside it. Run any script with `--help` for flags.

## Development

The repository is a uv workspace whose root publishes the `bro` distribution from `bro/`; `bro-dev/` is the one other member. `./setup.sh` syncs the workspace and installs the repository hooks; `source .venv/bin/activate` then puts third-party development tools and every console script on `PATH` as bare commands. The root owns the formatter, test gate, pytest config, and type/dependency policy for both distributions:

- `./format.sh` — format and autofix the whole repository
- `./run-tests` — console-script drift, lint, deptry, pyright, unit tests, and the two host-only docker smoke stages: the container entrypoint's postconditions and the launch path from a cold image tag (`--no-docker` skips both). It must pass cleanly before changes are pushed
- `pytest bro/launch/e2e_test.py` — live Docker launch e2e, separate from the default suite
- `BRO_LLM_TESTS=1 pytest bro/bros/dev/commit_llm_test.py` — live-LLM behavior probes (`*_llm_test.py`): a real bro against the configured provider, asserting on the artifacts it produces. They spend real tokens, so they stay outside the default roster and are collected-but-skipped without the explicit env var
- `sync-scripts --project <directory>` — regenerate a distribution's `[project.scripts]` and committed `_entrypoints.py`, then `uv sync --all-packages --all-groups --all-extras`
- `uv build --package bro` and `uv build --package bro-dev` — build the wheels

The repository root carries `pyproject.toml` (framework distribution metadata, the workspace table, and the tool config both distributions run under), `conftest.py` (test isolation), `dev/run_tests.py` (the explicit test roster), and `README.md` (consumer-facing install and extension contract). The development style policy is `bro/prompts/dev/style.md`, tool-served to dev sessions as `dev-style-source::read`; shell scripts follow `bro-dev/bro_dev/shell_policy.py` (prelude sourcing, shebang), enforced repository-wide by `shell_policy_test.py`. Agent commits carry the token-accounting footer automatically — the installed `commit-msg` hook appends it whenever the environment carries an agent usage source, and human commits stay footerless (`bro/workflow/commit_footer.py`); never hand-write or strip it. `bro/setup/setup_env.sh` is a host-prerequisite reference and is invoked by nothing.

## Layout

Package-source paths in this section are relative to `bro/`.

- `bro.py` — `BaseBro` ABC (the framework) and the framework helpers (`BroRaised`).

  Subclasses set `name`, `description`, and class-level `system_prompt = "..."` plus optionally `data_sources = [...]` and `mcp_servers = [...]`. An `mcp_servers` entry is a tool-pack module (resolved through its conventional `spec` Toolset to the full roster), a bare `Toolset`, or an `bro.llm.mcp.MCPServerSpec` from a scoping call such as `project_tools.mcp.spec('search')`; every form normalizes to the pure-metadata manifest (secrets plus a `build()` factory) via `bro.llm.mcp.as_spec` at collection. Entries in `mcp_servers` and `data_sources` may be wrapped with `bro.base.condition.when(...)` to gate them on the assembling surface's facts, e.g. the dev toolset's `when(harness == 'bro', dev.mcp)` because claude has built-in file and shell tools. Conditions are decided where composition happens (`bro.llm.mcp.select`, harness `bro`), so an unmatched entry never mounts and its spec never builds (conditioning reference: `bro/reference/conditions.md`). Live servers are built lazily, once, when the bro first runs tools (`_live_mcp_servers()`), so metadata surfaces (credential scoping, prompt composition, `bro show`) never construct them and a live server's constructor may hold real resources — released through `MCPServer.close()` when the bro's lifetime ends, so a session leaves no process of its own behind.

  `BaseBro.__init__` walks the MRO from base to most-derived class and concatenates each class's own `mcp_servers`, `data_sources`, and `system_prompt`. A `ReviewDev(Dev)` subclass declares only what it adds; Dev's own entries flow through automatically, and the `features` map merges along the same walk with derived classes overriding per name. The legacy `super().__init__(system_prompt=...)` escape hatch remains for callers that need a dynamic prompt computed at instantiation; a bro that wants the current time can instead pull it through the `CurrentTime()` data source.

  **Features.** `features` is the class-level map of named optional capabilities — feature name → the gate deciding whether it's on: a `Condition` over the environment's resolvable credentials (`creds.contains('brog')`) or a plain bool constant (`True` pins it on; `False` disables it terminally — a descendant re-enabling a disabled feature fails construction). The declaration feeds a `#features` vocabulary (`BaseBro.vocabulary()`) into every surface the bro renders or assembles, so `when(feature('brog'), bro.brog.mcp)` entries and `{{iff #features contains brog}}` text switch together, and a gated component joins `needed_secrets()` only where its gates resolve. Dev's `brog` feature is the built-in example: the tracker toolset, task-workflow script branches, and tracker prompt fragment all ride it. Semantics: `bro/reference/conditions.md` "Bro features".

  `BaseBro` also auto-prepends every `bro/prompts/shared/*.md` to the system prompt and appends a `## Data sources` block describing each declared `DataSource`. When the bro has any namespaced tools or scripts it also appends the tool-name rule (`bro/prompts/tool_names.md`, templated on the `#wire` scheme), and closes the prompt with the tool-grounding fragment (`bro/prompts/grounding.md`), whose directives render its body only into the claude-bare flavor (see `bro/prompts/CLAUDE.md`). Each composed flavor renders once with its surface facts (`bro.llm.mcp.render_text`: harness `bro`, the flavor's wire, the environment's credentials) — the wire is where the flavors diverge: `system_prompt` (bro-native LLM runs) renders `bare` (`namespace::tool` resolves to the wire name `namespace__tool` the bro's tool list carries), while `claude_system_prompt` (what `cw ss --raw` passes as claude's `--system-prompt`) renders `mcp`, because there each namespace is mounted as an MCP server and the wire names are `mcp__namespace__tool`. The bro's own class prompts (MRO-concatenated, before those additions) are kept as `persona`; `bro/cw/system_prompt.py:_session_append_prompt` injects it plus the shared script instructions into every cw-session (the `--bro` bro, defaulting to the project default) so it carries that bro's policies and canonical script invocation contract without running under `--raw`.

  **LLM spec.** `llm_spec` is a class-level attribute holding the bro's `LLMSpec` — a provider-specific frozen dataclass (e.g. `bro.llm.llms.chat_gpt.LLMSpec` with typed `model`, `reasoning_effort`, `service_tier`) that carries the knobs the LLM accepts and validates them in `__post_init__`. Default is `chat_gpt.LLMSpec()` (gpt-5, no reasoning effort, no service tier); each bro overrides the whole spec at class level. Construction-time overrides go through `BaseBro.create(spec)` — it instantiates the class then replaces `llm_spec`, so subclass constructors never have to forward anything. Specs also expose `dump()` → dict / `LLMSpec.from_dict(data)` for serialization round-trip; `from_dict` eagerly imports the known providers so dispatch works in processes that haven't pulled the provider module in themselves.

  **Scripts and skills.** The bro-native procedure store lives under `<bro_pkg>/scripts/*.md` and composes by MRO with derived overrides. A script's flat frontmatter may declare a one-line JSON parameter map (`parameters: {"task": "task ref", "notes?": "optional context"}`); the `?` suffix marks an optional string parameter. `bro/scripts.py` validates the store and builds the reserved `at` MCP namespace on every surface with scripts; each script is one canonical `@::<name>` tool, and its full frontmatter description stays on that tool. When OpenAI resolves, the server also mounts `@::@`: a prompt-backed structured `mu` call interprets free text against the script roster, and the tool returns the resolved script's rendered instructions with the interpreted arguments, or an expected error. Bro-native and `cw ss --raw` builds additionally mount the reserved `@::skill(name)` framework tool because those harnesses have no native third-party skill loader; its current skill set is empty, so valid calls return an empty body. Their composed `## Skills` block maps third-party `/<name>` requests to that loader. An ordinary cw persona session keeps Claude's own skill mechanism and mounts neither the framework loader nor script-to-`SKILL.md` adapters. `bro show` lists only the bro's script roster.

  **Run-start credential gate.** `run()` / `send()` refuse to start when any name in `missing_secrets()` — the manifest plus the LLM key — doesn't resolve, listing all missing names: `run()` raises `BroRaised`, interactive surfaces reply with the report. The optional tier stays best-effort.

  **Interactive vs non-interactive paths.** Runs at the unattended hold — `bro.run()`'s default, and the `bro run` / `ask` / summon default with it — expose a built-in `raise` service tool — the agent calls it to abort with a reason when the request cannot be fulfilled (missing credentials, no appropriate tool, contradictory constraints, unclear/uninterpretable input); the call raises `BroRaised(reason)` out of `bro.run()`. The claude service builds (`claude_bro_mcp_servers` / `claude_persona_mcp_servers`) mount `raise` too when the session is unattended and killable (`BRO_HOLD=unattended` + `CW_RUNNER_PID` in the environment — cw's in-place runner exports them), in the tool's mcp-wire flavor: no exception can abort the consuming claude session, so the call emits `completed{result, end_reason: raised}` over the broker channel where one exists, then terminates the session via `bro.workspace.session.terminate_session` (SIGTERM to the in-place runner, forwarded to claude — same delegation shape as `banner` → `bro.workspace.banner.render_banner`). The abort stays machine-readable after the fact through the recorded trail — the raise call with its reason is the transcript's last record, and `bro.trails.record.claude` ends the session's trail as `raised` with that reason as `end.detail`. `_system_prompt_for` appends the matching hold fragment via `bro.prompts.hold_fragment` (`run()` defaults to unattended, `send()` to guided, and every launch surface overrides per its `--hold` — defaults in `bro/launch/CLAUDE.md`, "Launch holds"; the level files are documented in `bro/prompts/CLAUDE.md`, "Hold text"), so the hold is injected at run start, never runtime-detected. Every other hold mounts no `raise` — the injected fragment tells the agent how to involve the human instead, down to guided's ask-clarifying-questions convention on the interactive paths (`bro.send()`, the `bro chat` / `call` CLIs). Both service builds always mount a `banner` tool — the session environment facts of `cw banner --llm` rendered in-process (`bro.workspace.banner.render_banner`, with the bro's name passed explicitly — an in-process run's environment carries the launcher's `CW_BRO`, or none), so every bro detects its environment without a shell; the playbook is `bro/prompts/environment.md`. Both service builds also mount the summon tools when the process has a broker channel (`BROKER_CHANNEL` set), forwarding to `bro.summon` — every wait run off-loop via `bro.base.offload.off_loop` so interactive surfaces stay responsive: `summon` blocks and relays the target's answer or failure (`detach: true` returns the request id right after the send instead), taking the same child-shaping knobs the launcher flags carry (`grant` / `revoke` / `effort` / `fast` beside `timeout` / `into` / `hold`), and `summon_check` checks on a request id — a non-marking peek by default (`{state: pending|completed|collected, …}`), a cursor read with `last_seen` (replays the conversation from that sequence — the recovery path when a result was read by a wait whose reply never arrived), `wait: true` to block and collect. The blocking modes own their per-call channel client on the loop and close it in `finally`, so a cancelled tool call (an MCP client that timed out or aborted) unblocks the worker thread instead of leaving a ghost waiter holding the broxy route — the terminal then buffers for a later check. Both descriptions carry a `{{when #wire = mcp}}` transport-caution block, rendered at service-server build — service tools are harness features, the one tool surface whose rendering vocabulary gets the system `#wire` fact injected next to the `#tools` roster: the MCP-served builds (`wire == 'mcp'`: persona and `--raw` claude sessions, consumed over streamable HTTP with a client-side call budget (claude's `MCP_TOOL_TIMEOUT`, set by cw's runner)) render a caution steering long runs to `detach` + polling, whose lost-request-id recovery forks on whether `summon_list` is mounted; the in-process `bare` builds render the plain contract. When the session also carries a summon-status file (`CW_SUMMON_STATUS` set), `summon_list` mounts alongside them, reporting the session's summons with their request ids (`summon.list_summons`) — the rediscovery surface when a request id was lost with a dead client.

  **Observing.** Non-interactive runs stream a live trace of reasoning summaries, tool calls, tool outputs, and assistant text to stderr — timestamped plain log lines via `bro.llm.observer.BoringRenderer` by default, or colored `rich` panels via `RichConsoleRenderer` when `--rich` is passed (`ask --rich`, `bro run --rich`); both honor `observer=` on `BaseBro.run` for explicit overrides. Subclasses override `_make_observer()` to set the default observer; test bros return `NullObserver()` for silence.

  Assistant text flows through `on_assistant_message(text, terminal)` with the flag distinguishing mid-stream chatter (interim, model is still calling tools) from the terminal reply (also returned from `LLM.send`). `BoringRenderer` / `RichConsoleRenderer` render both — terminal as `reply` (bright), interim as `assistant`. Callers that already render the return value themselves (e.g. `bro.launch.call`'s `TextRenderer` / `TUIRenderer`) branch on `terminal=True` and skip to avoid double-emitting.

  **Credential manifest.** `bro.needed_secrets()` is the bro's component credential manifest — the union of each declared MCP server spec's and data source's `needed_secrets` plus the bro's MRO-collected `extra_secrets`. It is harness-aware: `needed_secrets(harness='claude')` counts only components whose conditions hold on that harness, matching what `claude_persona_mcp_servers()` mounts. It deliberately excludes the LLM key (`llm_spec.needed_secrets()`): surfaces that run the bro as an LLM process add it, while a claude-code session uses its own authentication. Components declare credentials through pure metadata (`WebSearch` → `brave`; `chat_gpt.LLMSpec` → `openai`); `extra_secrets` is the escape hatch for environment needs no component expresses. The host hydrates the per-surface set into a scoped credential store before a container starts, and missing required secrets fail on the host. Full mechanics: `bro/reference/cw.md` ("Scoped credential hydration"). `bro show` renders the features, manifest, optional tier, LLM key, and per-surface baseline note.

  **Optional credential tier.** `bro.optional_secrets()` is the best-effort sibling of the manifest — the union of each declared component's `optional_secrets`, plus OpenAI when the bro has scripts, minus `needed_secrets()` so a hard requirement is never downgraded. It is for credentials a capability uses when present but degrades without, such as the LLM key behind a `SearchableDataSource`'s query-focused summary or the scripts dispatcher. The host hydrates it via `build_scoped_store(optional=...)`; resolvable names are materialized and absent optional names are skipped. `bro.base.credentials.available(name)` is the presence predicate behind runtime gates and feature directives in static text. Separately, `needs_docker` is a plain class attribute, defaulting to `False`, for personas whose tools require the host Docker socket; the host grants the socket to a `--raw` or bro-run container only when it is set, while claude code sessions receive it unconditionally.

  **Usage publishing.** `_create_llm` passes `agent=bro.agent` (the `bro//<name>` surface identity), so the provider publishes its cumulative per-model usage under that identity to the env-pointed usage file (`bro.llm.usage`) after every LLM call. Tool subprocesses inherit the pointer, which is how `bro/workflow/commit_footer.py` credits a native bro run's commits — the file carries the agent identity itself rather than leaning on the environment — an in-process run's `CW_BRO` is the launcher's, not the bro's.

  **Recording.** Each `BaseBro.run()` or first `.send()` opens a trail through a `bro.llm.tracker.Tracker` and emits the opening `system_prompt` step. The bro's context-managed lifetime ends that trail once with clean → `ok`, `BroRaised` → `raised`, and other exceptions → `error`; `run()` supplies its own lifetime, while interactive owners keep one around the conversation. The same tracker is plumbed into the LLM so provider implementations record the replayable native stream. The default factory builds a `bro.trails.record.bro.Recorder` from the `trails` secret; recording is mandatory in production, while `NullTracker` is explicit through `TRAILS_DISABLED`, a per-run argument, or `set_default_tracker_factory`. `run()`, `send()`, and `bro.fork.fork()` require the caller to name the driving `surface`. The framework revision is recorded as `configs.VERSION`; `bro/trails/CLAUDE.md` owns the recording subsystem.
- `shell.py` (`bro-shell-dir`) — validates the packaged shell helpers and prints their installed directory for shell consumers
- `summon.py` (`summon`) — peer-side summon wire contract plus the blocking, detached, check, and list client surfaces; host enforcement lives in `launch/summon_control.py`
- `channel.py` — `BroChannel`, the bro-side broker consumer: a thin adapter over `bro.broker.client.Client` emitting the run lifecycle to the host dispatcher. `BaseBro.run()` builds one via the `_make_channel()` hook (`BroChannel.from_env()` — `None` when `BROKER_CHANNEL` is unset or the broker package is unimportable; the broker imports are deferred to call time, so importing `bro` never requires broker) and emits `started{trail_id}` right after `start_trail` and `completed{result, end_reason}` after `end_trail`, with `result` defined per end reason (ok → the run's return value, raised → `BroRaised.reason`, error → the exception string). Fires only for `BaseBro.run` (LLM-process children): interactive `send()` emits nothing, and a claude-code `--raw` session never calls `run()`. `close()` confirms delivery (`ClientTransport.close(confirm=True)`) — the lifecycle terminal is typically the process's last act before exit. `conftest.py` drops `BROKER_CHANNEL` so tests never emit into a live session channel.
- `bros/` — one package per concrete agent (`bros/<name>/__init__.py`); `bros/__init__.py` declares the `BRO_SPECS` map (`name -> "module:ClassName"`) the registry loads lazily.

  `bros/bro/` defines the concrete `Bro(BaseBro)` — the minimal bro registered as `bro`, with a minimal go-to system prompt and no MCP servers. **All other bros inherit from this `Bro`** (not `BaseBro` directly), so they pick up the shared defaults via the MRO walk; inherit from `BaseBro` only when you want to opt out of those defaults. It owns the shared scripts every bro inherits (`bros/bro/scripts/`): `@::ask` — the summon UX: phrasing → target + self-contained prompt, client pick (`bro run --summon` / its `summon` alias vs the `summon` service tool), foreground-vs-background, failure relay (protocol and enforcement live in `bro/summon.py` and `bro/launch/summon_control.py`, not in the script) — and `@::reflect` — post-mortem of the session or a given incident into durable-improvement proposals (script / toolset / prompt / doc edits), each delivered as a task or, when small, fixed in place.

  Framework personas:
  - `dev/` — generic developer with file/shell/search tools from sibling `mcp.py` (`bash` and `grep` shell out, file ops are thin Python; `spec` is the dev `Toolset`, tools registered via `@spec.tool`; see sibling `REFERENCE.md` for output windowing and background-job behavior). It owns `@::audit` plus the task-driven `@::fix`, `@::run-pr`, and `@::land` scripts inherited by dev-derived bros. Tracker bookkeeping rides the optional `brog` feature; the pinned `commit-accounting` feature has session-start provisioning (`BaseBro._provision_workspace`, cw's runner) install the commit-footer hooks into managed workspaces
  - Consumer personas register through the `bro` entry-point group and live in their contributing packages
- `datasources/` — `DataSource` ABC + `SourceUnavailable` (`bro.base.py`) + connectors to read-only sources. The base ABC declares `name`, `summary`, `namespace` (a property, `f'{name}-source'`), `needed_secrets` / `optional_secrets`, and `as_mcp_server()`. The `SearchableDataSource` subclass (`searchable.py`) adds the canonical `search` + `fetch` pair, exposed as bare `search` / `fetch` tools inside the source's `<name>-source` namespace (wire name `<name>-source__search`). Subclasses implement `search` and `_fetch_content(id)` (raw record); the base `fetch(id, query=None)` returns the raw record when no query is given and otherwise summarises it for the query via `mu` (one `source_summary` prompt for every source). That summary path reads the LLM key, so `SUMMARY_SECRET='openai'` is a base-level `optional_secret` (best-effort, hydrated when present); with it absent, a non-null `query` raises rather than silently returning raw text. The fetch tool's description advertises which mode is live via a `#features` directive (see "Optional credential tier" above). Subclass `DataSource` directly for sources that don't fit the search/fetch shape and override `as_mcp_server()`, stamping `self.namespace` onto the returned server. Currently:
  - `http.py` — shared HTTP transport for the sources (`get_json` / `get_text`): throwaway per-request sessions with a tight timeout and the common User-Agent
  - `wikipedia.py` — Wikipedia REST API; `_fetch_content` returns the article extract (base layers the query summary)
  - `web_search.py` — Brave Search; needs the `brave` secret
  - `current_time.py` — current local date and time; single `get_time` tool (wire `current-time-source__get_time`)
  - `references.py` — ready-made `FileSource` instances over the repo's canonical reference docs (`environment` → `bro/prompts/environment.md`, `template` → `bro/reference/template.md`, `conditions` → `bro/reference/conditions.md`, `dev-style` → `bro/prompts/dev/style.md`); a bro mounts one by listing it in `data_sources` (Dev mounts `dev-style`; derived bros can add the others)
  - `file.py` — `FileSource(name, summary, path, render=True)`: surface a static reference file as a single `read` tool (wire `<name>-source__read`) whose description carries the summary. One rendering is read by every harness, so the body must be surface-neutral — `read` renders with no facts and a `#harness` directive raises; `render=False` serves the file verbatim, for a doc whose payload is the directive syntax itself. Use for canonical docs the bro consults on demand; the ready-made instances live in `references.py`
- `registry.py` — process-wide registry of bro classes: `register(cls)`, `get_class(name)`, `create_bro(name, llm_spec=None)`, `list_classes()`, `known_names()` (every resolvable name, read without importing any bro module — what `bro/launch/summon_control.py` validates summon targets against). `create_bro` returns a fresh instance every call. Lookup is lazy: a miss imports only the one bro module named in `BRO_SPECS` — or, when that map misses, named by an installed distribution's `bro` entry point (the out-of-tree registration path; an external name shadowing a built-in raises) — so resolving one external bro never pulls in another's dependency graph; only `list_classes()` (i.e. `bro list`) imports them all. Tests flip the module-level `_autoload` off to isolate the registry to hand-registered bros
- `fork.py` — fork of a recorded trail. `replay_messages` rebuilds the provider input through the selected fork point and follows `forked_from` ancestors when needed; `latest_fork_point` chooses the newest consistent point. `fork(..., surface=<caller>)` requires the driving program's surface and opens the child trail with `ForkedFrom(trail_id, step_id)`. Same-provider/model forks at an `llm_call` use the provider's `previous_response_id`; every other case replays the prefix client-side. Consumed by `call --resume` (`--at <step_id>` overrides the fork point).
- `run.py` (`bro`) — lightweight CLI dispatcher: `bro run` and `bro chat` import the shared launcher implementations in `launch/` only when selected; `bro list` and `bro show <name> [--system-prompt]` remain metadata paths (card renderer in `show.py`)
- `launch/` — the launch machinery behind `bro run` / `bro chat` and their compatibility aliases (`ask`, `call`): the container hop, the chat UIs, and `call --resume`; see `launch/CLAUDE.md`

## Extension entry points

Installed distributions extend the framework through `bro` (personas), `bro.credential_sources` (minting source types), `bro.credentials` (registry entries), `bro.brog.backends` (task-tracker backends), and `bro.toolsets` (standalone MCP toolsets). Declarations are installation metadata: run `uv sync` after adding or removing an entry point; editing an already-declared target module needs no reinstall. Name-keyed groups load only the matching entry, while credential-registry assembly loads every `bro.credentials` contribution, so those target modules must remain import-cheap.

## Adding a Bro

Create `bros/<name>/__init__.py` with `from bro.bros.bro import Bro` and a `class YourBro(Bro)` (inherit from the concrete `Bro` so you pick up the shared defaults; use `BaseBro` only when you want to opt out). Declare `name`, `description`, and `system_prompt` as class attributes; add tool sources as class attributes too:

- `system_prompt = "..."` — class-level. When you `class B(A)` and both declare `system_prompt`, `__init__` concatenates A's then B's (MRO base-to-derived) so subclasses only declare their *additions*.
- `data_sources = [YourSource()]` for read-only data connectors
- `mcp_servers = [project_tools.mcp]` for a contributing package's full toolset (a tool-pack module stands for its full roster)
- `mcp_servers = [project_tools.mcp.spec('search', 'update')]` to scope to specific tools (validated at declaration)
- `mcp_servers = [when(harness == 'bro', dev.mcp)]` (`from bro.bros import dev`) for the developer toolset (file/shell/search tools; roster in `bro/bros/dev/mcp.py`), gated off the claude harness as in `Dev`'s own declaration; scope to specific tools with `dev.mcp.spec('bash', ...)`
- Roster-based servers are declared as an `bro.llm.mcp.Toolset` in their module — tools register via `@spec.tool`, secrets via the static `secrets` class var or a `get_secrets` override when the set depends on the selected tools; `MCPServerSpec.of(ServerClass, *ctor_args)` is the manifest escape hatch for irregular server classes
- `mcp_servers` and `data_sources` are also walked along the MRO and concatenated, so a `ReviewDev(Dev)` subclass declares only its additional components and retains Dev's toolset.
- An entry in either list may be gated on surface facts: `mcp_servers = [when(harness == 'bro', spec)]` (`from bro.base.condition import when`, `from bro.llm.mcp import harness`; `when` also accepts a plain bool for a genuinely static predicate) — or choose among alternatives with `iff(c1, a1, c2, a2[, e])`, which raises when nothing matches and no else item is given. Conditions evaluate at assembly, so an unmatched entry never mounts and its spec never builds — see `bro/reference/conditions.md`. Declarations skip the `ClassVar` annotation — BaseBro's class-level declarations carry the types; ruff's RUF012 is ignored for `bro/bros/*/__init__.py`.
- `llm_spec = chat_gpt.LLMSpec(...)` (or any other provider's `LLMSpec`) overrides the LLM recipe. Per-instance overrides go through `YourBro.create(spec)`.
- `extra_secrets = ('github',)` declares credentials no component expresses (a bro's environment needs). MRO-walked and unioned like `mcp_servers`; folded into `bro.needed_secrets()`, which the host hydrates into the scoped container store. Most secrets come from the declared MCP servers / data sources / `llm_spec` and need no entry here — see "Credential manifest" above.
- `features = {'brog': creds.contains('brog')}` declares named optional capabilities — feature name → the gate deciding whether it's on: a `Condition` over the environment's resolvable credentials (`from bro.llm.mcp import creds`), or a plain bool (`True` pins it on, `False` disables it; MRO-merged, derived wins per name, and `False` is terminal — descendants cannot re-enable). Gate components with `when(feature('brog'), …)` (`from bro.bro import feature`) and text with `{{iff #features contains brog}}`; a gated component's secrets enter the manifest only where its gates resolve. See `bro/reference/conditions.md` "Bro features".
- `may_summon = ('reviewer',)` declares which bros this bro may summon — its static outgoing allow-list, adjusted per launch by `--grant @bro` and `--revoke @bro`. A summoned child may name only bros its summoner could summon, so widening is explicit and bounded by the host's depth cap. The declaration is MRO-walked and unioned like `extra_secrets`; each seed expands the transitive launch authority and should be added deliberately.
- Drop markdown files into `bros/<name>/scripts/*.md` (flat frontmatter with `name`, `description`, an optional one-line JSON `parameters`, and an optional informational `version` bumped when the script changes; markdown body after the closing `---`) to declare scripts. Filename stem is canonical and validated against `name:`; script and parameter names must fit the wire charset, script stems `at` / `skill` and parameter name `offset` are reserved, and malformed declarations fail at load. Script names are imperative verb phrases (`fix`, `land`, `run-pr`, `run-feature`), kebab-cased when multi-word. Scripts follow the same MRO walk as `system_prompt` and `mcp_servers`: each ancestor contributes, derived classes override parents on name collision, and anything under `bros/bro/scripts/` is inherited by every bro. The full description is the tool description; keep it useful for tool selection rather than optimizing its first sentence.

**Register the new bro manually** — add one entry to `BRO_SPECS` in `bros/__init__.py` (`'your-name': 'bro.bros.your_pkg:YourBro'`). There is no auto-discovery; the map entry is required for `create_bro('your-name')` to work. The key must equal the class's `name` attribute — the registry validates this when it lazily imports the module, and the map itself carries no imports, so adding a bro never slows startup for the others.

A bro living outside the framework repository registers through the `bro` entry-point group: the consumer project's pyproject declares `[project.entry-points.bro] your-name = "your.module:YourBro"`, and the registry resolves the name in any environment that installs both distributions. An external name may not shadow a built-in, and the key must equal the class's `name`. Package-relative scripts and MRO-collected declarations work across distributions. Project launch defaults (`[tool.bro] default`, image repository) are documented in `bro/reference/cw.md`, "Per-project defaults".

## Adding a DataSource

Set `name` (slug) and `summary` (one-line; injected into the system prompt of every Bro that uses it). For the common search/fetch shape, subclass `SearchableDataSource` and implement `async search(query, limit) -> list[Hit]` and `async _fetch_content(id) -> str` (the raw record). The base provides `fetch(id, query=None)`: it returns the raw record when no query is given and otherwise summarises it for the query via `mu` — so you don't write summarisation per source. That summary path depends on the `openai` key, declared once on the base as an `optional_secret`; with the key absent a non-null `query` raises (no raw-text fallback). For other shapes (e.g. a singleton fact like `current_time.py`), subclass `DataSource` directly and override `as_mcp_server()` to expose whatever tools fit. When an upstream HTTP/network failure makes the source temporarily unusable, raise `bro.datasources.base.SourceUnavailable(source, reason)` rather than letting raw transport exceptions escape — the agent loop turns it into a tool result the model can route around. If the source reads a credential through the store, declare it with `needed_secrets = ('catalog',)` (or `optional_secrets` for one it degrades without) so the host hydrates it into any bro that uses the source (see "Credential manifest"). Bind to a Bro by declaring `data_sources = [YourSource()]` on its class.
