# bro/launch/CLAUDE.md

Bros launching and managing layer. It owns the shared launch machinery behind the canonical `bro run` / `bro chat` verbs and their compatibility aliases, plus the bro-aware host machinery every launch surface (these CLIs and `cw ss` alike) runs a session through: per-surface credential scoping, summon enforcement, and the broker-root composition over the `bro/workspace/` layer's spawners.

## Files

- `ask.py` (`ask`) — the `ask` console script, a thin alias of `bro run`. Both select the trails display `ask` preset: live activity is rendered to stderr and exactly one undecorated terminal reply to stdout; `--rich` changes activity to lazy Rich panels without changing those routes.

  Input passes through verbatim, `/<name>` invocations included: the bro's `## Skills` prompt maps that syntax to the framework `bro::skill` loader, with the rest treated as arguments to the returned instructions. There is no client-side expansion or validation; an empty body means the requested skill is unavailable.

  Ctrl+C cancels a run through the loop — the tool call in flight takes its process group with it — and `run_main` turns the re-raised `KeyboardInterrupt` into exit 130, so an interrupted run reads as an interrupted command rather than a crash.
- `call.py` (`call`) — the canonical `bro chat` implementation and its thin `call` alias; drives an interactive `bro.send()` conversation.

  The initial message passes through verbatim like every later REPL turn — a `[[ask reviewer …]]` command reaches the spell interpreter as-is (see `ask.py`).

  Auto mode embeds the Textual trail view in `call_tui.py` when both stdin and the conversation output are TTYs and the UI dependencies are installed. It falls back to the conversation stream frontend when either stream is redirected or the dependency is absent; `--text` forces that frontend. The Textual shell keeps the message field, clipboard-on-selection, Shift+Enter line breaks, Ctrl+D quit, backtick stats modal, and turn cancellation, while the embedded view owns the scrollable history, message/reasoning/tool widgets, dates, and animated transient status.

  **Interrupting a turn.** Either mode can stop the bro mid-thought, mid-tool-call, or mid-wait and take a new message — Esc or Ctrl+C in the TUI, Ctrl+C in the text REPL — and both render the stopped turn as `⨯ interrupted` (`call.INTERRUPTED_NOTICE`). What that costs the conversation is the provider's business (`bro/llm/CLAUDE.md`, `openai.py`): the model resumes knowing its calls were abandoned. The TUI disables the message field for the length of a turn, so a second concurrent `send` on one conversation is impossible and no message queues up for a bro the user has already changed their mind about — the interrupt is the way back to the field. In text mode the SIGINT handler is installed only around a running turn, so Ctrl+C at the `> ` prompt still ends the chat.

  The Bro's interactive machinery picks up automatically in both modes: the surface's hold fragment injected into the system prompt (guided for `bro chat`, attended for `call` — see "Launch holds"), with no `raise` tool at either.

  **Opening banner.** Both modes submit the visual `cw banner` (`bro.workspace.banner.render_banner`) as an explicitly trusted surface notice before the user's initial message, so it follows the display path without entering the LLM conversation. The stream frontend preserves its ANSI and the Textual renderer decodes it into a selectable bro bubble; arbitrary notices and tool content remain plain data. The bro name is passed to `render_banner(bro=…)` so the logo renders on an in-process (`--in-place`) run too, whose environment carries the launcher's `CW_BRO` or none. The launch line preserves the outer `bro chat` or alias spelling.

  **Display.** `call` and `bro chat` select their separately named trails-display presets. One `DisplaySession` consumes normalized resume records and the live adapter's events for the full conversation; terminal completion therefore renders exactly once through the same path as interim text, reasoning, and correlated tool activity. The text mode supplies `StreamRenderer`; `ChatApp` supplies the lazy `bro.trails.display.textual.TextualRenderer` over its embedded `TrailView`. Banner, transient activity, interruption, and fallback turn-error records enter that session as surface state. Closing or cancelling a turn removes transient activity before the owning display lifetime ends.

  **Resume.** A chat conversation is recorded as a trail (surface `call`; on exit the CLI prints the trail id with the matching pickup command), so quitting doesn't lose it: `bro chat <bro> [what] --resume [TRAIL_ID]` (or `call`) continues an explicit trail, or the bro's newest recorded call when the value is omitted. `what` is optional with `--resume`. Machinery in `resume.py`: the bro is preseeded via `bro.fork.fork` at the trail's latest consistent step (`latest_fork_point`), the continuation is recorded as a new `call` trail with a `forked_from` pointer, and `conversation_history` returns the shared recorded adapter's normalized, exact-index-bounded records. The selected call/chat preset renders those records before live events. Runs the bro class's current spec, not the recorded spec; same-model resumes continue server-side via `previous_response_id`, anything else replays client-side. Mutually exclusive with `--no-trails`.

  Flags: `--text` and `--resume` belong only to `bro chat` / `call`; the launch, LLM, scope, and trail flags parallel `bro run` — see "Naming the LLM". Every launcher also takes `--hold` — see "Launch holds". The `ask` and `call` aliases imply `--fast` — they are the human-facing spellings, where someone waits on the reply — so every other launch of a bro (the canonical verbs, summoned children) runs at normal speed unless it is asked for.
- `llm_flags.py` — the LLM-selection flag set every surface registers (`add_llm_flags`), the `--llm` preset store, and the two per-surface resolvers. See "Naming the LLM".
- `resume.py` — `call --resume` machinery: latest-call-trail lookup, normalized recorded conversation history, and `resume()` orchestration.
- `call_tui.py` — Textual `ChatApp` shell: `MessageInput`, `StatsScreen`, display-session lifetime, async `bro.send()` worker, and cancellation. The worker runs on the app loop under `@work(exclusive=True)`, so interrupt and quit can cancel it and wait for the agent loop to unwind; the trail widgets and selection implementation live with the renderer in `bro.trails.display.textual`.
`bro/run.py` dispatches the canonical verbs here with function-local imports so metadata commands such as `bro list` do not import the launcher stack.

## Naming the LLM

Every launch surface — the canonical verbs and their aliases, `cw ss` (and `dive-in` through `bro/cw/flags.py`), and the summon request — registers one flag set from `llm_flags.py`: `--provider`, `--model`, `--effort`, `--fast`, and the `--llm` that speaks for all four and excludes them. `--llm` takes `provider:model:effort` with an optional `+fast` suffix and any field left empty (`:fable5`, `::high`, `openai:sol:max+fast`), or a preset name — a repo declares presets in its `[tool.bro.llm]` table and the host overrides them per name in `~/.bro.json`'s `llm` table.

Whatever the flags spell, the surface collapses it into that one canonical value (`canonicalize`) before reconstructing any argv, so the preset table and the provider inference are read exactly once, host-side: a container, a resumed session, and a summoned child all receive a settled recipe. The four piece flags never travel.

A surface then resolves the value over its own standing recipe. `resolve_native` puts it over the bro's `llm_spec` for an LLM-process run; `resolve_claude` puts it over Claude Code's own default for a session. Each refuses a provider it cannot run, naming the surface that can — the flags choose a model, not an execution harness, so `bro run --provider claude-code` points at `cw ss --raw` rather than switching harnesses. The resolved recipe also reaches `scope.scoped_secrets`, so a launch hydrates the key of the provider that will actually answer.

## Launch holds

Every launcher forwards `--hold` — the run's user-involvement level, whose fragment `BaseBro` injects into the system prompt and which gates the `raise` service tool (unattended only; semantics in `CLAUDE.md`, "Interactive vs non-interactive paths"). An omitted flag resolves to the surface's own default:

- `bro run`, `ask`, and the summon path (`bro run --summon` / bare `summon` / the `bro::summon` service tool) — `unattended`; a summon carries the flag in its request payload only when explicitly set, so the child's own default applies otherwise

- `bro chat` — `guided`

- `call` — `attended`; because it diverges from its canonical verb's default, `chat_main` always forwards the resolved hold into the container hop's inner argv

The claude-session surfaces resolve their own defaults the same way (`cw ss` → guided, `dive-in` → attended or guided with `--host`; `bro/reference/cw.md` and `bro/reference/dive_in.md` own those).

## Host machinery

The modules the launch surfaces share — consumed by `maybe_containerize` here and by `bro/cw/session.py` for `cw ss`; none of them import `cw`:

- `scope.py` — per-surface launch scoping: `Surface` (cw-session / raw session / bro run) and its `_RECIPES` table feeding `scoped_secrets(bro_name, surface, llm_spec=…)` (the credential scope of a launch running as the bro — one computation for every surface, so they cannot drift; the resolved recipe replaces the bro's declared one, so a run against another provider hydrates that provider's key), `bind_project_credentials` (bind the resolver to the operated project's instance selection, which computing a scope does first so every host-side reader of the launch agrees on which instance a kind means), `preflight_scoped_launch` (finalize grant/revoke overrides + summon allow-list + strict store hydration, any failure raised as `LaunchScopeError` for the caller's own error surface), `launch_view_store` (the preflight's lazy counterpart: the finalized scope as a kinds-only read-through `credentials.scoped_view_store`, for host-side code — e.g. dive-in's task prefetch — that reads a credential on the session's behalf before the launch exists), `split_scope_overrides` (the unified `NAME` / `@BRO` value grammar, split by kind), and `summoned_credential_scope` (a summoned child's scope under its request's credential overrides — read by the spawner lowering that child's launch and by the host control bounding what the child may grant onward). The tier mechanics live in `bro/workspace/store.py`; the per-surface sets are documented in `bro/reference/cw.md` "Scoped credential hydration"
- `summon_control.py` — summon, host side: `summon_allow_list` (an effective outgoing allow-list, `(may_summon ∪ grants) − revokes`, every name validated against `bro.registry.known_names()` — computed at launch for a session root, and per request for a summoned child) and `SummonControl`, the per-root enforcement + bookkeeping the broker root wires up (payload validation, per-peer authorization with the depth cap, the `SummonLaunchSpec` spawn, the delivery-tap observer, and the visibility outputs — host log lines plus the per-session audit/status files under `var/cw/summon/`). The wire contract is owned by `bro/summon.py`; broker imports stay function-local — the module sits on the pre-gate launch path
- `bro_run.py` — `describe`, the shared broker-free bro-run launch description: the `bro.workspace.docker.Launch` for `bro <verb> <bro> … --in-place` (inner command, env with bro git identity + `CW_BRO`, stdio/docker knobs) over a caller-computed credential scope, so every surface that spawns a bro run composes it identically — consumed by `maybe_containerize` and the summon lowering, each bringing the scope its own path resolved through `scope.py`
- `root.py` — `run_in_container`: run a neutral `Launch` directly or as the broker's supervised root peer, behind `bro.workspace.containers`' lazy-import gates (the fallback prepares + attaches without any broker import)
- `spawn.py` — the post-gate broker-root composition: `run_root_via_broker` (the composite over both launch modes plus summon lowering, the root-lifecycle log handlers, and the per-root `SummonControl` wiring) and the summon lowering itself (`SummonLaunchSpec` → `bro_run.describe` off-loop, the child's workspace recorded throwaway, base ref resolved from the summoner's workspace HEAD or the request's `into`, the request's credential grant/revoke finalized over the child's computed scope, the resolved allow-list stamped into the child's environment as its own `CW_MAY_SUMMON`, and its `--hold` / `--llm` on the child's inner argv). Imports broker at module level, which is why only the gated paths import it
- `identity.py` — `bro_git_identity_env(bro_name)`, the git identity every managed session commits as
- `e2e_test.py` — the launch-stack e2e against the real docker daemon (host-only, isolated HOME/workspace root; kept out of `PYTEST_FILES`)

## Container isolation

On the host, `bro run` and `bro chat` re-exec the bro into a throwaway cw-style container; `ask` and `call` forward into the same paths. The shared hop is `maybe_containerize` in `_cli.py`: it computes `bro_run.describe`'s launch and passes it to `root.run_in_container`. The pinned inner argv uses the canonical verbs — `bro run … --in-place` or `bro chat … --in-place` — so a clone based on a ref that predates them fails loudly at the inner parse rather than running old code (the same policy as `cw ss`'s outer↔inner contract in `bro/reference/cw.md`). The launch carries the target bro's scoped credentials, `CW_BRO`, and bro git identity.

The workspace clone bases on the host checkout's current `HEAD`; `--into <ref>` selects another resolvable commit. Uncommitted changes never transfer. `--into` also rides `--summon`, while an in-place run rejects it because no clone is created.

Inside a container there is no implicit downgrade or relay. `bro run` (and its aliases) refuses unless the caller chooses `--summon` for an isolated broker-launched child or `--in-place` for the current process and scope. `bro chat` / `call` refuses unless `--in-place`, because chat is interactive while summon is one-shot. Refusal messages name the remedies.

`bro run --summon` delegates to `bro.summon`'s `relay_summon` / `summon_detached` functions and accepts `--timeout`, `--into`, `--hold`, `--detach`, plus the run-shaping `--grant` / `--revoke` and the LLM flag set — applied to the summoned child instead of a local run and carried in the request payload, the LLM set as its one canonical `llm` value; parser constraints reject only local rendering and trail flags. Bare `summon <target> <prompt>` forwards to this mode, while `summon check` / `summon list` remain channel-management commands. The `ask` alias's implied `--fast` applies to its summoned child too — the alias is the spelling where a human waits on the reply, whichever mode answers it.

`--grant <name>` / `--revoke <name>` (repeatable, on both canonical verbs and their aliases) adjust the run's launch scope before the hop. A plain name is a credential, adjusting both tiers of the scoped set: a grant joins the required tier when its kind is absent, or replaces the selected same-kind name (`--grant brog+github` selects that instance); a revoke removes the exact name from whichever tier contains it. Use a plain grant for a required credential that is not in the persona's manifest, or revoke a best-effort secret such as `openai` with `--revoke openai`.

A leading `@` marks a bro summon target, adjusting the run's summon allow-list instead: effective list = `(may_summon ∪ granted) − revoked` (`summon_control.summon_allow_list`, applied by the hop's launch-scope preflight over the run bro's MRO-collected `BaseBro.may_summon` defaults), with every name additionally validated against the bro registry so a typo fails at launch. The list is passed beside the neutral launch to `root.run_in_container` for the container's broker root — e.g. `call researcher --grant @reviewer "…"` lets that run summon `reviewer` even when its persona has no static seed.

Both kinds are strict — granting the exact selected name, granting one credential kind twice, or revoking a name absent from its scope errors and stops; an unknown credential grant still fails loudly at hydration — and host-side only (not threaded into the inner command), so `maybe_containerize` applies them when it hops and errors when it wouldn't (`--in-place` — the requested run creates no new credential scope and no broker root to adjust).

In summon mode the same two flags shape the *child's* scope, resolved host-side by the supervisor rather than the client: the `@bro` half against the child bro's own `may_summon` seeds on the broker loop (a malformed or no-op override is denied outright, and the resolved list is what the child's own summons are then authorized against), the credential half against the child's computed scope in the summon lowering (`spawn.py:_lower_summon`), where a bad override fails the launch. Both halves land in the summon audit as the summoner issued them.

Widening there is per request and bounded by the summoner: nothing of a summoner's scope is inherited unless its `grant` names it, and it can only name what it holds itself — a bro outside its own allow-list, or a credential outside its own scoped set, is denied. So authority only ever narrows down a summon chain, and the launch flags remain the one place it widens.

`--no-trails` turns recording off for either canonical host-side container hop: `maybe_containerize` has `bro_run.describe` set `TRAILS_DISABLED` in the launch env (the in-container tracker factory then returns `NullTracker`) and drop `trails` from the scoped set. It acts only on the container hop, so it's mutually exclusive with `--in-place`; and unlike `--llm` / `--text` it isn't forwarded into the inner argv — the env var carries the effect in. The recovery use case (deploying `trails-server` through a bro) and the `--in-place` alternative (`TRAILS_DISABLED=1` in the shell) are in `bro/trails/CLAUDE.md`.
