# bro/launch/CLAUDE.md

Bros launching and managing layer. It owns the shared launch machinery behind the canonical `bro run` / `bro chat` verbs and their compatibility aliases, plus the bro-aware host machinery every launch surface (these CLIs and `cw ss` alike) runs a session through: per-surface credential scoping, summon enforcement, and the broker-root composition over the `bro/workspace/` layer's spawners.

## Files

- `ask.py` (`ask`) — the `ask` console script, a thin alias of `bro run`.

  Input passes through verbatim, `/<name>` invocations included: the bro's `## Skills` prompt maps that syntax to the framework `bro::skill` loader, with the rest treated as arguments to the returned instructions. There is no client-side expansion or validation; an empty body means the requested skill is unavailable.

  Ctrl+C cancels a run through the loop — the tool call in flight takes its process group with it — and `run_main` turns the re-raised `KeyboardInterrupt` into exit 130, so an interrupted run reads as an interrupted command rather than a crash.
- `call.py` (`call`) — the canonical `bro chat` implementation and its thin `call` alias; drives an interactive `bro.send()` conversation.

  The initial message passes through verbatim like every later REPL turn — a `[[ask reviewer …]]` command reaches the spell interpreter as-is (see `ask.py`).

  By default opens the Textual chat UI in `call_tui.py` (IM-style: scrollable history, left/right bubbles, error-colored bubbles for failed turns, timestamp + date separators, an animated status bubble — "Thinking for \<elapsed\>…" during an LLM roundtrip, "Calling \<tool\>…" / "Calling N tools…" while tool results are pending — mouse selection copies straight to the system clipboard, Shift+Enter breaks the line in the message field, Ctrl+D to quit, backtick (`) opens a stats modal). Falls back to text mode (`[HH:MM:SS] bro: <reply>` lines + `> ` prompt) when stdin/stdout isn't a TTY; `--text` forces it.

  **Interrupting a turn.** Either mode can stop the bro mid-thought, mid-tool-call, or mid-wait and take a new message — Esc or Ctrl+C in the TUI, Ctrl+C in the text REPL — and both render the stopped turn as `⨯ interrupted` (`call.INTERRUPTED_NOTICE`). What that costs the conversation is the provider's business (`bro/llm/CLAUDE.md`, `chat_gpt.py`): the model resumes knowing its calls were abandoned. The TUI disables the message field for the length of a turn, so a second concurrent `send` on one conversation is impossible and no message queues up for a bro the user has already changed their mind about — the interrupt is the way back to the field. In text mode the SIGINT handler is installed only around a running turn, so Ctrl+C at the `> ` prompt still ends the chat.

  The Bro's interactive machinery picks up automatically in both modes: the surface's hold fragment injected into the system prompt (guided for `bro chat`, attended for `call` — see "Launch holds"), with no `raise` tool at either.

  **Opening banner.** Both modes render the `cw banner` (visual form, via `bro.workspace.banner.render_banner`) as the first bro message, before the user's initial message — so the session's environment facts (container, workspace, host path, launch command) are visible up front. Display-only: it is not part of the bro's LLM conversation. Text mode prints the ANSI banner directly; the TUI decodes it with `rich.text.Text.from_ansi` and mounts it as a bro bubble (`MessageBubble` accepts a Rich renderable, not just a markup string, for this). The bro name is passed to `render_banner(bro=…)` so the logo renders on an in-process (`--in-place`) run too, whose environment carries the launcher's `CW_BRO` or none. The launch line preserves the outer `bro chat` or alias spelling.

  **Renderers.** Each mode ships its own `Observer` renderer rather than reusing `BoringRenderer` / `RichConsoleRenderer` — those write to stderr which Textual silently swallows during TUI runs, and their multi-line panels don't fit the conversational shape of the text REPL. `TextRenderer` (in `call.py`) renders one-liners matching the `[HH:MM:SS] bro …` aesthetic — `· thinking:` and the tool trace. Both modes share the tool-trace format (`_trace_format.format_tool_call`): a call is `→ namespace::tool(arg=value, …)` with the canonical tool name and every argument named, each value shown inline only while its compact form stays short and elided to `...` past that; the return is the bare `← namespace::tool`, payload dropped. `TUIRenderer` (in `call_tui.py`) mounts each event between the user and bro bubbles — reasoning as a lighter-themed thinking bubble carrying the full summary block, the tool trace as dim full-width `SystemBubble` rows. Assistant text is not trace: an interim message — text the model emits in the same leg as a tool call, so the turn goes on — renders exactly as a reply does, untruncated: the same conversation line in text mode, a bro bubble (mounted above the typing indicator) in the TUI. Both skip `on_assistant_message` when `terminal=True` — the reply is the value `bro.send` returns and is already rendered by `call_text` or by `ChatApp`; emitting again would double-render.

  **Resume.** A chat conversation is recorded as a trail (surface `call`; on exit the CLI prints the trail id with the matching pickup command), so quitting doesn't lose it: `bro chat <bro> [what] --resume [TRAIL_ID]` (or `call`) continues an explicit trail, or the bro's newest recorded call when the value is omitted. `what` is optional with `--resume`. Machinery in `resume.py`: the bro is preseeded via `bro.fork.fork` at the trail's latest consistent step (`latest_fork_point`), the continuation is recorded as a new `call` trail with a `forked_from` pointer, and prior exchanges across the fork ancestor chain render as history in both modes. Runs the bro class's current spec, not the recorded spec; same-model resumes continue server-side via `previous_response_id`, anything else replays client-side. Mutually exclusive with `--no-trails`.

  Flags: `--text` and `--resume` belong only to `bro chat` / `call`; the launch, LLM-spec, scope, and trail flags parallel `bro run`. Every launcher also takes `--hold` — see "Launch holds". Both canonical verbs run the bro's plain class spec by default; `--fast` opts into the provider's fast-mode knob, and `--effort` applies an explicit provider-neutral effort override. The `ask` and `call` aliases imply `--fast` — they are the human-facing spellings, where someone waits on the reply — so every other launch of a bro (the canonical verbs, summoned children) runs at normal speed unless `--fast` is passed. A bro whose spec has no fast equivalent falls back to the plain spec (the aliases imply fast without the user asking for it); an unsupported explicit effort override fails.
- `resume.py` — `call --resume` machinery: latest-call-trail lookup, `conversation_history` (the prior exchanges across the fork ancestor chain, as `HistoryMessage`s both UIs render), and `resume()` orchestrating the fork.
- `call_tui.py` — Textual `ChatApp` plus its widgets (`MessageInput`, `MessageBubble`, `BubbleRow`, `DateSeparator`, `TypingIndicator`, `StatsScreen`). Mounts the auto-growing multi-line `MessageInput` on the bottom (Enter submits, Shift+Enter breaks the line — terminal caveat in its docstring) and a `VerticalScroll` of bubbles above. `bro.send()` runs in a Textual `@work(exclusive=True)` — an *async* worker on the app's own loop, which is what a cancellation can reach (Textual cannot cancel a thread worker: the task unwinds while the thread runs on). Nothing below it blocks the loop, so the UI stays live for the whole turn and the renderer mounts its bubbles directly. `ChatApp` keeps that worker as the current turn: `action_interrupt` cancels it and waits for it to unwind, and `action_quit` does the same before exiting, so quitting never leaves work running behind a restored terminal. Bro replies render as markdown through `ChatMarkdown` — rich's `Markdown` with a content-hugging width measurement (so short bubbles don't stretch to their max-width) and unpadded code blocks. Rich markdown (rather than Textual's `Markdown` widget) is deliberate: Textual composites rich `link` styles into OSC 8 hyperlinks that the *host* terminal resolves (modifier-click). Copy-on-select rides Textual's built-in mouse selection (`ChatApp.on_text_selected`); `SelectableRichVisual` gives rich-renderable bubbles the selection support plain `RichVisual` lacks — hit-test offsets, highlight, and copy extraction through `_reflow.py`, which aligns the wrapped display lines with a second, unwrapped render so copied text keeps the message's own line breaks rather than the wrap points and padding of the on-screen rectangle
`bro/run.py` dispatches the canonical verbs here with function-local imports so metadata commands such as `bro list` do not import the launcher stack.

## Launch holds

Every launcher forwards `--hold` — the run's user-involvement level, whose fragment `BaseBro` injects into the system prompt and which gates the `raise` service tool (unattended only; semantics in `CLAUDE.md`, "Interactive vs non-interactive paths"). An omitted flag resolves to the surface's own default:

- `bro run`, `ask`, and the summon path (`bro run --summon` / bare `summon` / the `bro::summon` service tool) — `unattended`; a summon carries the flag in its request payload only when explicitly set, so the child's own default applies otherwise

- `bro chat` — `guided`

- `call` — `attended`; because it diverges from its canonical verb's default, `chat_main` always forwards the resolved hold into the container hop's inner argv

The claude-session surfaces resolve their own defaults the same way (`cw ss` → guided, `dive-in` → attended or guided with `--host`; `bro/reference/cw.md` and `bro/reference/dive_in.md` own those).

## Host machinery

The modules the launch surfaces share — consumed by `maybe_containerize` here and by `bro/cw/session.py` for `cw ss`; none of them import `cw`:

- `scope.py` — per-surface launch scoping: `Surface` (cw-session / raw session / bro run) and its `_RECIPES` table feeding `scoped_secrets(bro_name, surface)` (the credential scope of a launch running as the bro — one computation for every surface, so they cannot drift), `bind_project_credentials` (bind the resolver to the operated project's instance selection, which computing a scope does first so every host-side reader of the launch agrees on which instance a kind means), `preflight_scoped_launch` (finalize grant/revoke overrides + summon allow-list + strict store hydration, any failure raised as `LaunchScopeError` for the caller's own error surface), `launch_view_store` (the preflight's lazy counterpart: the finalized scope as a kinds-only read-through `credentials.scoped_view_store`, for host-side code — e.g. dive-in's task prefetch — that reads a credential on the session's behalf before the launch exists), `split_scope_overrides` (the unified `NAME` / `@BRO` value grammar, split by kind), and `summoned_credential_scope` (a summoned child's scope under its request's credential overrides — read by the spawner lowering that child's launch and by the host control bounding what the child may grant onward). The tier mechanics live in `bro/workspace/store.py`; the per-surface sets are documented in `bro/reference/cw.md` "Scoped credential hydration"
- `summon_control.py` — summon, host side: `summon_allow_list` (an effective outgoing allow-list, `(may_summon ∪ grants) − revokes`, every name validated against `bro.registry.known_names()` — computed at launch for a session root, and per request for a summoned child) and `SummonControl`, the per-root enforcement + bookkeeping the broker root wires up (payload validation, per-peer authorization with the depth cap, the `SummonLaunchSpec` spawn, the delivery-tap observer, and the visibility outputs — host log lines plus the per-session audit/status files under `var/cw/summon/`). The wire contract is owned by `bro/summon.py`; broker imports stay function-local — the module sits on the pre-gate launch path
- `bro_run.py` — `describe`, the shared broker-free bro-run launch description: the `bro.workspace.docker.Launch` for `bro <verb> <bro> … --in-place` (inner command, env with bro git identity + `CW_BRO`, stdio/docker knobs) over a caller-computed credential scope, so every surface that spawns a bro run composes it identically — consumed by `maybe_containerize` and the summon lowering, each bringing the scope its own path resolved through `scope.py`
- `root.py` — `run_in_container`: run a neutral `Launch` directly or as the broker's supervised root peer, behind `bro.workspace.containers`' lazy-import gates (the fallback prepares + attaches without any broker import)
- `spawn.py` — the post-gate broker-root composition: `run_root_via_broker` (the composite over both launch modes plus summon lowering, the root-lifecycle log handlers, and the per-root `SummonControl` wiring) and the summon lowering itself (`SummonLaunchSpec` → `bro_run.describe` off-loop, the child's workspace recorded throwaway, base ref resolved from the summoner's workspace HEAD or the request's `into`, the request's credential grant/revoke finalized over the child's computed scope, the resolved allow-list stamped into the child's environment as its own `CW_MAY_SUMMON`, and its `--hold` / `--effort` / `--fast` on the child's inner argv). Imports broker at module level, which is why only the gated paths import it
- `identity.py` — `bro_git_identity_env(bro_name)`, the git identity every managed session commits as
- `e2e_test.py` — the launch-stack e2e against the real docker daemon (host-only, isolated HOME/workspace root; kept out of `PYTEST_FILES`)

## Container isolation

On the host, `bro run` and `bro chat` re-exec the bro into a throwaway cw-style container; `ask` and `call` forward into the same paths. The shared hop is `maybe_containerize` in `_cli.py`: it computes `bro_run.describe`'s launch and passes it to `root.run_in_container`. The pinned inner argv uses the canonical verbs — `bro run … --in-place` or `bro chat … --in-place` — so a clone based on a ref that predates them fails loudly at the inner parse rather than running old code (the same policy as `cw ss`'s outer↔inner contract in `bro/reference/cw.md`). The launch carries the target bro's scoped credentials, `CW_BRO`, and bro git identity.

The workspace clone bases on the host checkout's current `HEAD`; `--into <ref>` selects another resolvable commit. Uncommitted changes never transfer. `--into` also rides `--summon`, while an in-place run rejects it because no clone is created.

Inside a container there is no implicit downgrade or relay. `bro run` (and its aliases) refuses unless the caller chooses `--summon` for an isolated broker-launched child or `--in-place` for the current process and scope. `bro chat` / `call` refuses unless `--in-place`, because chat is interactive while summon is one-shot. Refusal messages name the remedies.

`bro run --summon` delegates to `bro.summon`'s `relay_summon` / `summon_detached` functions and accepts `--timeout`, `--into`, `--hold`, `--detach`, plus the run-shaping `--grant` / `--revoke` / `--effort` / `--fast` — the flags below, applied to the summoned child instead of a local run and carried in the request payload; parser constraints reject only local rendering and trail flags. Bare `summon <target> <prompt>` forwards to this mode, while `summon check` / `summon list` remain channel-management commands. The `ask` alias's implied `--fast` applies to its summoned child too — the alias is the spelling where a human waits on the reply, whichever mode answers it.

`--grant <name>` / `--revoke <name>` (repeatable, on both canonical verbs and their aliases) adjust the run's launch scope before the hop. A plain name is a credential, adjusting both tiers of the scoped set: a grant joins the required tier when its kind is absent, or replaces the selected same-kind name (`--grant brog+github` selects that instance); a revoke removes the exact name from whichever tier contains it. Use a plain grant for a required credential that is not in the persona's manifest, or revoke a best-effort secret such as `openai` with `--revoke openai`.

A leading `@` marks a bro summon target, adjusting the run's summon allow-list instead: effective list = `(may_summon ∪ granted) − revoked` (`summon_control.summon_allow_list`, applied by the hop's launch-scope preflight over the run bro's MRO-collected `BaseBro.may_summon` defaults), with every name additionally validated against the bro registry so a typo fails at launch. The list is passed beside the neutral launch to `root.run_in_container` for the container's broker root — e.g. `call researcher --grant @reviewer "…"` lets that run summon `reviewer` even when its persona has no static seed.

Both kinds are strict — granting the exact selected name, granting one credential kind twice, or revoking a name absent from its scope errors and stops; an unknown credential grant still fails loudly at hydration — and host-side only (not threaded into the inner command), so `maybe_containerize` applies them when it hops and errors when it wouldn't (`--in-place` — the requested run creates no new credential scope and no broker root to adjust).

In summon mode the same two flags shape the *child's* scope, resolved host-side by the supervisor rather than the client: the `@bro` half against the child bro's own `may_summon` seeds on the broker loop (a malformed or no-op override is denied outright, and the resolved list is what the child's own summons are then authorized against), the credential half against the child's computed scope in the summon lowering (`spawn.py:_lower_summon`), where a bad override fails the launch. Both halves land in the summon audit as the summoner issued them.

Widening there is per request and bounded by the summoner: nothing of a summoner's scope is inherited unless its `grant` names it, and it can only name what it holds itself — a bro outside its own allow-list, or a credential outside its own scoped set, is denied. So authority only ever narrows down a summon chain, and the launch flags remain the one place it widens.

`--no-trails` turns recording off for either canonical host-side container hop: `maybe_containerize` has `bro_run.describe` set `TRAILS_DISABLED` in the launch env (the in-container tracker factory then returns `NullTracker`) and drop `trails` from the scoped set. It acts only on the container hop, so it's mutually exclusive with `--in-place`; and unlike `--fast` / `--text` it isn't forwarded into the inner argv — the env var carries the effect in. The recovery use case (deploying `trails-server` through a bro) and the `--in-place` alternative (`TRAILS_DISABLED=1` in the shell) are in `bro/trails/CLAUDE.md`.
