# llm/CLAUDE.md

Provider-agnostic LLM abstraction and MCP tooling that the `bro/` agent system and `flow/mcp/` build on. `LLM` is the chat interface; an `MCPServer` supplies callable `Tool`s; an `Observer` renders a run live while a `Tracker` records it durably. Run the `llm` CLI (`llm.py`) with `--help` to chat against a provider from the shell.

## Modules

- `llm.py` — the `LLM` ABC (`send(messages)`, holding a `ToolRegistry` + `Observer` + `Tracker` plus an optional `agent` identity) and the `LLMSpec` ABC: a frozen recipe (model + provider knobs) with `create_llm`, `needed_secrets`, an optional `.fast()` / `.with_effort(level)` (the neutral low/medium/high/xhigh/max effort vocabulary, mapped per provider), and a `dump` / `from_dict` round-trip keyed by a `TYPE` discriminator so a stored spec rehydrates. `cumulative_usage()` reports the instance's lifetime per-model counts in the four billed token classes (None for providers that don't track). Also the `llm` chat CLI.
- `mcp.py` — the tool layer. `Tool` / `MCPServer` ABCs, `FunctionTool` (wraps a Python function, deriving input + output schema via FastMCP's `func_metadata`), and `ToolRegistry` which assembles tools across servers under `namespace__tool` wire names (the canonical form is `namespace::tool`; harnesses resolve `::`→`__`, Claude Code additionally prepends `mcp__`). `validated_callable` / `validate_output` give the HTTP delivery path the in-process fail-fast guard against backend drift; `render_return_shape` renders a tool's output schema into its description; `render_text` renders `base.template` directives in static agent-facing text against the surface facts the call site knows — the consuming harness (`#harness` over `Harness`: `bro` / `claude` — a `--bro` session is the bro harness), the wire-name scheme (`#wire` over `Wire`: `bare` / `mcp`), and the environment's credentials (`#creds`, lazily probing `credentials.available` over the given universe). Servers declare `needed_secrets` / `optional_secrets`, unioned into a bro's hydration set; `MCPServerSpec` is the declaration-side counterpart — pure metadata (secrets + a `build()` factory) that hosts hold and read without constructing a live server, so live servers are free to own real resources. `Toolset[T]` is how a roster-based server module declares itself in one object (namespace + per-server `state` factory + secrets policy), with tools registering on it via the `@spec.tool('description')` decorator (returns the function unchanged, so tools stay directly callable): calling the toolset yields the scoped `MCPServerSpec`, `build()` the live server; the static `secrets` class var covers the common case and overriding `get_secrets(tool_names)` the derived one (flow). `Context[T]` is the per-call envelope a tool opts into by declaring a `Context`-annotated parameter — excluded from the derived schema and injected on every call carrying the server's long-lived `state` (how flow tools share one `System`); `MCPServerSpec.of(cls, ...)` stays as the manifest escape hatch for irregular server classes.
- `observer.py` — `Observer` ABC streaming run events (reasoning, assistant text, tool call / result) with renderers: `RichConsoleRenderer` (colored panels), `BoringRenderer` (plain text), `NullObserver` (no-op). `rich` is imported lazily so deployed images that never render need not ship it.
- `tracker.py` — `Tracker` ABC, the durable sibling of `Observer`: it ships the same event stream (as a *trail* of *steps*) to a sink. `NullTracker` (default), `LocalFileTracker` (JSONL), `HTTPTracker` (the production sink, POSTing to the deployed `trails-server`). The trail model, server, and reader CLI are owned by `trails/CLAUDE.md` — read that, not this, for the recording subsystem.
- `llms/` — provider specs / implementations, each pairing an `LLMSpec` subclass with its `LLM`:
  - `chat_gpt.py` — `ChatGPT` over the OpenAI Responses API (the real provider; `needed_secrets` → `openai`, `.fast()` → `service_tier='priority'`, `.with_effort()` → `reasoning_effort` with the shared levels mapping through and `max` capping at `xhigh`). Long runs can be bounded by server-side compaction: the spec's opt-in `compact_threshold` (default off) flows to `responses.create` as `context_management`, so the server compacts the chained context in-band once it crosses the threshold. After every `responses.create` it folds the response's `usage` into `cumulative_usage()` (cached input → `cache_read`, the uncached remainder → `input`, `cache_write` 0, reasoning inside `output`) and, when constructed with an `agent`, publishes the snapshot via the root `usage` module's env-pointed file.
  - `echo.py` — `Echo`, returns the last user message verbatim; the dependency-free default for tests and the `llm` CLI.

## Conventions

- A new provider lives in `llms/`, subclasses `LLMSpec` with a unique `TYPE`, and is added to `_ensure_providers_loaded` / `_spec_for_type` in `llm.py` so `from_dict` and the CLI can find it.
- Importing a provider module must stay cheap: every bro module constructs its `LLMSpec` at class-definition time, so the provider SDK (openai, …) is imported inside the functions that touch the API, never at module level. `chat_gpt.py` is the pattern — annotations resolve through a `TYPE_CHECKING` block, and the SDK enums a spec validates against are mirrored locally with a sync test pinning them to the SDK.
- A `Tool`'s `call` returns `str` for an unstructured tool or a JSON-ready `dict` for a structured one; raising `ToolControlSignal` (vs. a generic exception) escapes the agent loop instead of being fed back to the model as the tool result.
- Acronyms stay all-caps in identifiers (`LLMSpec`, `MCPServer`, `HTTPTracker`); `TYPE` discriminator strings are lowercase snake_case (`chat_gpt`, `echo`).
