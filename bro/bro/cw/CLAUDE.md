# cw/CLAUDE.md

`cw` launches claude in a managed workspace — either a host **worktree** or an isolated docker **container** clone. This package is the structural split of the former monolithic `cw.py`; behavior is unchanged. For *how it actually works* (subcommands, host vs container modes, credential seeding, env vars, `--resume`/`--bro`/`--auto`), read `reference/cw.md` — that document owns the behavior, this one owns the code layout.

## Module map

Leaf utilities (no intra-package deps, or only on each other):

- `constants.py` — `_CW_MODEL` (the claude model every session runs), `DEFAULT_SESSION_BRO` (the `--persona` default a cw-session runs as), and the bro git identity every cw-launched session commits as, with `bro_git_identity_env()` exporting it as the `GIT_AUTHOR/COMMITTER_*` env set. Its own module so consumers share them without a heavier import
- `git.py` — `git_out` (capture a git command's stdout) + `git_run` (the capture-output/text/env `subprocess.run` wrapper for git calls whose returncode/stdout is inspected) + `no_prompt_env` (`GIT_TERMINAL_PROMPT=0` overlay so git fails fast instead of prompting) + `rev_parse_commit` (ref → commit sha, `None` when unresolvable) + `resolve_ref` (ref → commit sha with an origin fetch when not local — the `--into` rule) + `resolve_head` (another local repo's HEAD → a commit sha present in this repo's store, fetching the objects from the repo path when foreign — the summon base-ref inheritance read); both fetches land in a nonce-named private `refs/cw/resolve-*` ref (read, deleted), so concurrent resolutions cannot read each other's result
- `paths.py` — project-root / worktrees-dir / containers-dir / broker control-dir / summon state-dir / host-log dir resolution, `_venv_env`, `_in_container`, `_session_claude_dir` (a session's `~/.claude/cw-sessions/<name>` state dir — the container `~/.claude` overlay, a host session's `CLAUDE_CONFIG_DIR` target), `_claude_config_dir` / `_encode_claude_path` / `_claude_projects_dir` (a workspace's claude projects dir under the session's config root — `CLAUDE_CONFIG_DIR` when set, else `~/.claude`; one derivation for both modes), `_latest_jsonl`
- `flags.py` — `add_forwarded_flags` / `extract_forwarded_argv` / `EFFORT_LEVELS`: the pass-through flag set `dive-in` forwards into `cw ss`
- `secrets.py` — scoped-credential logic (`_session_secrets` → a `ScopedSecrets(required, optional, docker_sock)` dataclass), `_finalize_secrets`, `_materialize_scoped_store` (a host session's on-disk scoped store, the `CREDENTIALS_REGISTRY` target), `_load_anthropic_key`, `_apply_claude_auth`, `_ppp_tarball`, the session baseline constant
- `summon.py` — summon, host side. `summon_allow_list` computes a session's effective outgoing allow-list (`(may_summon ∪ grants) − revokes`, strict via `credentials.apply_grant_revoke`, every name validated against the `BRO_SPECS` keys); every launch surface threads the result to `run_root_via_broker`. `SummonControl` is the per-root enforcement + bookkeeping `run_root_via_broker` wires up: the `summon` request handler (payload validation; per-peer authorization — the root against the launch-computed list above, a summoned child against its own bro's static `may_summon` seeds, attributed through the dispatcher `origin` topology + the control's spawn records, an unattributable peer denied; the `_MAX_SUMMON_DEPTH` nesting cap; denial as a correlated `reply{error}` plus a `deny` audit entry; the cheap `SummonLaunchSpec` spawn with the requesting peer as parent and its workspace path as the child's base-ref inheritance source — the root's from the session key, a child's from its `broker-<channel>` clone), the delivery-tap observer tracking each child's trail id and outcome, and the visibility outputs — a host log line per event, the per-session state files under `var/cw/summon/` keyed by the mode-prefixed session key the launch surface passes (`c:<name>` container / bare `<name>` host; `<key>.jsonl` audit + `<key>.status.json` live status, every entry naming its actual `summoner`; the status file is read by the statusLine via `CW_SUMMON_STATUS` — named by the shared `summon` module — pointing at the host path for a host session and through the read-only `/host-repo` mount for a container one), and the loud root-teardown log for children killed in flight. Broker imports stay function-local — the module sits on the pre-gate launch path (see "Lazy broker import"); the wire contract (tag, payload keys, 1800s default timeout) is owned by the top-level `summon` module
- `mcp.py` — session-local HTTP MCP serving: `MCPEndpoint` (the port + bearer token a server listens on), `_http_mcp_config` (the claude mcp-config json for a set of namespaces), and `_start_session_mcp_server` / `_SessionMCPServer` (the runner-owned `mcp-server <spec> --http --port 0` lifecycle: OS-assigned port via port file, the `wait_healthy` /health gate, terminate on session exit)
- `broxy.py` — host-mode session broxy launch: `_start_session_broxy` / `_SessionBroxy` (the host side of the one shared broxy sequence: spawn `broxy serve` on a session-tempdir socket, gate on `broxy await`, terminate on session exit; returns `None` with a warning when the broxy cannot run, after which the runner unsets `BROKER_CHANNEL` — the session gets no channel). No broker import — the daemon and the gate are the `broxy` console script (`broker/broxy.py`), so the module stays importable where broker is not
- `claude_config.py` — per-session claude config state, both modes: `_write_session_settings` (the constructed session settings both modes write; a container session adds the bypass-permissions pre-accept), `_seed_claude_json` (the explicit seed-once `.claude.json` — container mounts it, host reads it via `CLAUDE_CONFIG_DIR`), and `_provision_host_claude_dir` (the host session's private state dir: seeded json + settings + first-run plugins copy + legacy transcript migration); `reference/cw.md` "Host claude-state isolation" owns the behavior
- `system_prompt.py` — `_load_base_prompts` / `_session_append_prompt` (the `--append-system-prompt` text)
- `listen.py` — the `cw.listen` console script: the Stop-hook listener every session runs (wired by `claude_argv.py` through the merged `--settings`) — reconstructs the finished turn from the transcript and runs audit handlers over it, the first finding blocking the stop with corrective feedback. The sole handler today is the tool_use guard, firing on a turn that narrates tool calls its real `tool_use` blocks cannot account for (structural gate, `mu` extraction of the narrated calls, code-side comparison); mechanism and guard abstain on unreliable evidence
- `session_context.py` — `build_session_context` / `encode_session_context`: the typed launch-context records (system prompt, git state, MCP servers, root CLAUDE.md) the in-place session runner captures into `CW_SESSION_CONTEXT` for `sync-session-log` → `rewind`
- `session_log.py` — `_start_session_log_sync` / `_SessionLogSync`: the runner-owned `sync-session-log --watch` daemon lifecycle — continuous transcript upload next to claude for every session flavor, stderr to `<claude config dir>/session-log-sync.log`, terminate-on-session-exit as the final sync (`reference/cw.md` "Session-log sync" owns the behavior)

Workspace inspection + docker mechanics:

- `docker.py` — thin docker wrappers (`running_mounts`, `find_container_id` — takes the mount `Path` so this stays a dependency-free leaf), image build (`_image_tag` / `_ensure_image`), `_docker_create_argv`, `_create_container` (create + scoped-store `docker cp`, shared by `containers.py` and `spawn.py`), and the forwarded-env set
- `workspace.py` — the `Workspace` ABC (`HostWorktree` / `ContainerWorkspace`) owning the host/container duality for inspection + teardown (`path`, `ref`, `is_active`, `is_clean`, `remove`, `claude_projects_dir`, `subject` / `last_active`, the `from_ref` / `all` factories). The shared clean *policy* is one `_check_clean(runner, refresh_origin)` parameterized by a `_GitRunner` each subtype supplies (status-env, ancestry-env, head-ref provider, `bring_in_submodule_head` hook — container's alternate-objects dance lives in `ContainerWorkspace._git_runner`, a no-op on host). Kept as module-level helpers: the thin `_format_ref` / `_parse_ref` / `_CONTAINER_PREFIX` (banner + `exec_in_workspace` need format/parse without an instance), `_host_path_is_clean` (the host policy on an arbitrary path — `cw check-clean` with no ref), `_host_pidfile`, `_read_subject`, `_last_active`, and `_cleanup_image` / `_remove_container_dir` (the force-rmtree-with-root-escalation + image-discovery teardown primitives `ContainerWorkspace.remove` composes)
- `banner.py` — `cw banner`: the `SessionFacts` dataclass (the typed session facts both renderers read — `collect` classmethod ← env + /.dockerenv, `render_visual` / `render_llm` methods, `display_ref` property) + `render_banner` + the prompt-split / logo constants

Launch + lifecycle:

- `containers.py` — container launch (`run_in_container`) and `exec_in_workspace`, plus the broker gates: the mode-neutral `_broker_enabled` and the container-flavor `_container_broker_enabled` (adds the docker-daemon constraint — a macOS daemon runs in a VM and can't bind-mount the host channel socket). `run_in_container` runs the session as the root peer of a broker — `_run_root_via_broker` builds the attached `DockerLaunchSpec` and delegates to `spawn.run_root_via_broker`; the post-exit finish runs after the broker returns — unless the gate (`BROKER_DISABLED` set, broker unimportable, or a macOS host) degrades it to the direct `docker start -a -i`
- `spawn.py` — cw's adapters for broker's async `Spawner` port, plus `run_root_via_broker`, the root-peer launch both session modes share (one broker over `var/cw/broker`, the built-in ping handler, the root-lifecycle log handlers (a root run's `started`/`completed` land in the host log — the host process is the root's parent), the root's `SummonControl` — allow-list from `may_summon`, session identity from `session` — registered as the `summon` handler + delivery observer with its killed-in-flight log once the loop ends (a finally, so an unwinding exception still logs), supervise until the root exits; the spawner is a `CompositeSpawner` dispatching on the concrete `LaunchSpec` type over both launch modes plus summon, so any root — host process or container — can spawn docker children). `SummonLaunchSpec` (the request fields + the summoner's workspace path, cheap to build on the loop) is lowered by `SummonSpawner` off-loop via `_lower_summon` — the target's own `bro_run_secrets` scope, `ask <target> "<prompt>"`, `CW_BASE_REF` from the summoner's workspace HEAD (`resolve_head`) or the request's `into` ref, an unresolvable input raising into the correlated `failed{reason: 'launch'}` — then delegated to the docker path. `DockerSpawner` reads the concrete `DockerLaunchSpec`: either launch mode runs the blocking prepare — `_ensure_image` (a rebuild can take minutes), scoped-store build, `docker create` via `_docker_create_argv` + `_create_container` — off-loop through `asyncio.to_thread`, with the provisioned channel socket → `/run/broker.sock` and `BROKER_CHANNEL` pointed at it, then attaches `docker start` as an asyncio subprocess — the non-TTY child (`start -a`, stdout and stderr merged into one pipe and drained by an async task into a bounded ring buffer for `failed{output_tail}`; the ambient `_DOCKER_FORWARD_ENV` forwards switched off, so its environment is the `LaunchSpec` snapshot only; a derived `broker-<channel>` throwaway workspace is removed once the child ends) vs the interactive root (`start -a -i`, inherited stdio, the ambient forwards on — it is the launcher's own session — a SIGINT forwarder and a TTY-gated host-output redirect to `var/cw/log/<session>.log` for the attach's lifetime (`_HostLogRedirect` — mid-session host lines and spawner shell-out chatter must not paint over the session's raw-mode UI), container teardown on client exit, empty `output_tail`). `ProcessSpawner` reads `ProcessLaunchSpec`: the host-session root as a plain subprocess with inherited stdio, `BROKER_CHANNEL` pointing straight at the provisioned socket (no bind-mount hop). Not in the hub re-export — only `containers._run_root_via_broker` and `session._run_host_root_via_broker` consume it, function-locally (see the lazy-broker-import invariant)
- `worktrees.py` — host worktree create / provision
- `listing.py` — `cw list` (one loop over `Workspace.all(project)`; keeps the `ThreadPoolExecutor` fan-out — mounts fetched concurrently with the per-workspace subject/last_active reads)
- `clean.py` — `cw clean` (one `_assess` over `Workspace.all(project)`; keeps the fan-out — host worktrees assessed concurrently with the `docker ps` mounts fetch, containers once it resolves)
- `bro.py` — `_populate_bro_skills` (surfacing bro skills as claude-harness-rendered `SKILL.md` copies)
- `claude_argv.py` — `build_claude_launch`, the one claude argv builder for both flavors: the cw-session/bro switch (`--bare` + bro system prompt + `mcp__ns__*` allow-list vs the cw-injected append prompt), the merged `--settings` (fastMode + the `cw.listen` Stop hook + the workspace's `setup/print_anthropic_key.sh` as apiKeyHelper), and the single handling of `--model` / `--effort` / mcp-config / prompt seeding. Returns `ClaudeLaunch` (argv + the session-shaping prompt text for CW_SESSION_CONTEXT)
- `runner.py` — `run_in_place`, the inner session runner behind the help-suppressed `cw ss --in-place`: assumes cwd is a prepared workspace and owns everything next to claude — the host-mode private claude state dir (via `cw.claude_config`, exporting `CLAUDE_CONFIG_DIR` before anything derives paths; a container's mounts already provide it), cwd-derived `--resume` resolution, the host-mode session broxy (via `cw.broxy`, rewriting `BROKER_CHANNEL` — or unsetting it when the broxy cannot run — before the MCP server and claude inherit it; skipped in a container, where the entrypoint launched the broxy), the session-local MCP server (via `cw.mcp`, /health-gated — `bro:<name>` under `--bro`, `persona:<name>` for a cw-session), skills tmpdir + `--add-dir`, CW_SESSION_CONTEXT, the bro git identity + CW_BRO exports, SIGTERM forwarding, and the session-log sync daemon (via `cw.session_log`, started after the session context is set and stopped after claude exits)
- `session.py` — the `SessionSpec` dataclass (the parsed session parameters; `to_command_argv` builds `CW_COMMAND` / the resume hint, `resume_variant` clears the create-only inputs, `to_in_place_argv` serializes the inner runner invocation) plus the outer launch layer: `_replace_resume_hint` (the post-exit overwrite of claude's exit hint with `CW_RESUME_COMMAND`, both modes), and `start_session` dispatches to `_container_session` (container machinery only; the in-place invocation crosses docker as the container command, resolved from the clone's venv) or `_host_session` (the cw-session `claude_code` gate, scoped-store hydration, worktree ensure + provision, the private claude state dir + `CLAUDE_CONFIG_DIR` + `CREDENTIALS_REGISTRY` in the runner env, then the workspace's own `<worktree>/.venv/bin/cw ss --in-place …` — supervised as the broker's root peer (a `ProcessLaunchSpec`) behind the `_broker_enabled` gate, direct `subprocess.run` when the gate degrades), and the `--into` resolution in `start_session` (without it a new workspace bases on the host checkout's current HEAD — the entrypoint's fallback in container mode, `git worktree add … HEAD` in `_ensure_host_worktree` for host mode)
- `cli.py` — `build_parser` + `main` (policy gates, the `--in-place` dispatch to `runner.run_in_place`); `__cli_name__ = 'cw'` registers the `cw` alias on top of the canonical `cw.cli` script

## Workspace duality

The package's central concept is a *workspace backed by either a host worktree or a container clone*. That duality is expressed as the `Workspace` ABC in `workspace.py` (`HostWorktree` / `ContainerWorkspace`), which absorbs the host/container branching for the inspection + teardown surface — the call sites (`listing.py`, `clean.py`, `cli.py` check-clean, `session.py` resume/resume-hint) loop over `Workspace` objects instead of threading a `container: bool` and forking on it. The boundary stops at inspection/teardown: **launch** stays plain functions (`session.py`'s `_host_session` / `_container_session`, over `worktrees.py` and `containers.run_in_container`) that only *consume* a `Workspace` for the session guard and the post-exit resume hint / `--drop` removal.

## Invariants

- **Hub re-export.** `__init__.py` re-exports exactly the cross-package surface that `do/`, `dive_in.py`, and the bro service server (`bro::banner` → `render_banner`) consume (`run_in_container`, `render_banner`, `add_forwarded_flags`, `extract_forwarded_argv`, `EFFORT_LEVELS`, `DEFAULT_SESSION_BRO`, `bro_run_secrets`, `summon_allow_list`, `bro_git_identity_env`, `resolve_ref`, `_project_root`, `_worktrees_dir`, `_containers_dir`, `build_parser`). Those callers import these function-locally / patch them by the `cw.<name>` path, so the hub keeps them untouched — don't shrink it without checking `do/` (it patches `cw.run_in_container` in many test sites) and don't hoist `do/`'s function-local `cw` imports to module level (that would bind the name before a test can patch it).
- **Submodule → submodule imports.** Intra-package code imports `from cw.<module> import …`, never `from cw import …` / `import cw` — going through the hub mid-initialization is a partial-init hazard.
- **Lazy bro import.** `bro.registry` is imported function-locally (in `secrets`, `system_prompt`, `bro`) so `import cw` stays cheap — `dive_in.py` imports `cw` at module top level and the hub aggregates every submodule, so a module-level `bro.registry` import would tax every importer.
- **Lazy broker import.** The broker package is imported function-locally in `containers.py` and `session.py`, behind the `_broker_enabled` gate: `BROKER_DISABLED` — and an environment whose venv can't import broker — must short-circuit *before* any broker import, or the kill-switch couldn't save a launch that the import itself crashes. `spawn.py` imports broker at module level, which is why it stays out of the hub and is only imported past the gate.
