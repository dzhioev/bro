# do/CLAUDE.md

Bros launching and managing layer — thin helpers that drive a `Bro` toward a specific outcome. Each file is a single-purpose CLI wrapper; this package is the home for whatever orchestration shows up next.

## Files

- `do.py` (`ask`) — `async do(bro, what)`; forwards to `bro.run(what)` (one-shot). CLI: `ask <bro-name> <what>` (aliased to `ask` rather than `do` since `do` is a shell keyword; `do.do` also works).

  Input passes through verbatim, `/skill` invocations included: the bro's system prompt (`bro/bro.py:_render_skills`) describes the /-syntax — a message starting with `/<name>` invokes the skill of that name, the rest is its arguments — and the model loads the body itself via the `bro::skill` tool. There is no client-side expansion or validation; an unknown `/<name>` fails at the tool (which lists the available skills) and the bro raises.
- `call.py` (`call`) — entry point for an interactive chat with a bro.

  The initial message passes through verbatim like every later REPL turn — a leading `/ask devoops …` reaches the bro as-is and resolves through the /-syntax described in its system prompt (see `do.py`).

  By default opens the Textual chat UI in `call_tui.py` (IM-style: scrollable history, left/right bubbles, timestamp + date separators, animated "Typing…", mouse selection copies straight to the system clipboard, Ctrl+D to quit, backtick (`) opens a stats modal). Falls back to text mode (`[HH:MM:SS] bro: <reply>` lines + `> ` prompt) when stdin/stdout isn't a TTY; `--text` forces it. The text REPL helper `call_text(bro, initial)` is library-callable.

  The Bro's `interactive=True` machinery picks up automatically in both modes: no `raise` tool, the guided session-mode fragment injected into the system prompt.

  **Opening banner.** Both modes render the `cw banner` (visual form, via `cw.render_banner`) as the first bro message, before the user's initial message — so the session's environment facts (container, workspace, host path, launch command) are visible up front. Display-only: it is not part of the bro's LLM conversation. Text mode prints the ANSI banner directly; the TUI decodes it with `rich.text.Text.from_ansi` and mounts it as a bro bubble (`MessageBubble` accepts a Rich renderable, not just a markup string, for this). The bro name is passed to `render_banner(bro=…)` so the logo renders on an in-process (`--host`) run too, whose environment carries the launcher's `CW_BRO` or none.

  **Renderers.** Each mode ships its own `Observer` renderer rather than reusing `BoringRenderer` / `RichConsoleRenderer` — those write to stderr which Textual silently swallows during TUI runs, and their multi-line panels don't fit the conversational shape of the text REPL. `TextRenderer` (in `call.py`) renders one-liners matching the `[HH:MM:SS] bro …` aesthetic — `· thinking:`, `· says:`, `→ tool {args}`, `← tool {result}` — with JSON compacted to single lines. `TUIRenderer` (in `call_tui.py`) hops onto the app thread via `call_from_thread` and mounts dim full-width `SystemBubble` rows between user and bro bubbles for each event. Both skip `on_assistant_message` when `terminal=True` — the reply is the value `bro.send` returns and is already rendered by `call_text` (as the `[HH:MM:SS] bro: <reply>` line) or by `ChatApp` (as a bro bubble); emitting again would double-render.

  **Resume.** A `call` conversation is recorded as a trail (entry_point `call`; on exit the CLI prints the trail id with the pickup command), so quitting doesn't lose it: `call <bro> [what] --resume [TRAIL_ID]` continues a recorded conversation — an explicit trail id, or the bro's newest recorded call when the value is omitted. `what` is optional with `--resume` (sent immediately when given). Machinery in `resume.py`: the bro is preseeded via `bro.fork.fork` at the trail's latest consistent step (`latest_fork_point`), the continuation is recorded as a new `call` trail with a `parent` fork pointer (so resumes chain, and resume-latest picks up the continuation next time), and the prior exchanges — user messages + terminal replies, collected across the fork ancestor chain — render as history in both modes (TUI bubbles under their real date separators; `[HH:MM:SS] you|<bro>:` lines with `--- <date> ---` breaks in text mode). Runs the bro class's current spec (fast default, `--slow`/`--effort` as usual), not the spec recorded on the trail; same-model resumes continue server-side via `previous_response_id`, anything else replays client-side. Mutually exclusive with `--no-trails` (a resume both reads the recorded trail and records the continuation).

  Flags: `--text` forces text mode (above). `--resume` is `call`-only (above). `--slow`, `--effort`, `--host`, and `--no-trails` are shared with `ask`/`do-task` via `_cli.py` (`maybe_containerize` / `create_bro_for_run`); see "Container isolation". Fast mode is the default for these CLIs: the bro is built from `bro.llm_spec.fast()` — provider-specific (for ChatGPT it sets `service_tier='priority'`, the analog of Claude Code's `/fast`: same model/quality, faster, higher per-token price; see `llm/llms/chat_gpt.py`). `--slow` opts back out to the plain spec. Since fast is implicit (the user never explicitly asks for it), a bro whose spec has no fast equivalent silently falls back to the plain spec rather than erroring on `LLMSpec.fast()`.
- `resume.py` — `call --resume` machinery: latest-call-trail lookup, `conversation_history` (the prior exchanges across the fork ancestor chain, as `HistoryMessage`s both UIs render), and `resume()` orchestrating the fork.
- `call_tui.py` — Textual `ChatApp` plus its widgets (`MessageBubble`, `BubbleRow`, `DateSeparator`, `TypingIndicator`, `StatsScreen`). Mounts an `Input` on the bottom and a `VerticalScroll` of bubbles above. `bro.send()` runs in a Textual `@work(exclusive=True)` so the UI stays responsive while the LLM responds. Bro replies render as markdown through `ChatMarkdown` — rich's `Markdown` wrapped with a content-hugging width measurement so short bubbles don't stretch to their max-width. Rich markdown (rather than Textual's `Markdown` widget) is deliberate: Textual composites rich `link` styles into OSC 8 hyperlinks that the *host* terminal resolves (modifier-click). Copy-on-select rides Textual's built-in mouse selection (`ChatApp.on_text_selected`); `SelectableRichVisual` gives rich-renderable bubbles the selection support plain `RichVisual` lacks — hit-test offsets, highlight, extraction of the rendered text
- `do_task.py` (`do-task`) — `async do_task(bro, task)`; shorthand for `ask <bro> /fix <task>`. Wraps any non-slash input as `/fix <task>` and forwards through `do()`; if `task` already starts with `/` (e.g. `do-task ppp-dev "/pr <pr-url>"`), it passes through untouched. CLI: `do-task <bro-name> <task>`. A bro without a `fix` skill discovers that in-run at the `bro::skill` tool and raises (only `ppp-dev` exposes one today).

  When the task argument is a Notion page ref (URL or dashed UUID), `do-task` exports it as `CW_TASK_ID` before the container hop — the docker env forward list carries it in, so the run's `/pr` step resolves the commit footer's `Task:` line from it rather than re-deriving the task. Input that is no page ref (a description, a slash invocation) exports nothing and the run resolves the task itself. A host-relayed run (see "Container isolation") carries only the prompt, so the child resolves the task itself there too.

All modules expose their function for library use (`from do.do import do`, `from do.call import call_text`, `from do.do_task import do_task`) and as a CLI runnable via `python -m do.<module>` or the registered console scripts; CLIs resolve the bro name through `bro.registry.create_bro`.

## Container isolation

On the host, `ask` / `do-task` / `call` all re-exec the bro into a throwaway cw-style container (workspace `var/cw/containers/<cli>-<bro>-<hex>/`, dropped on exit) so the bro's tools operate on `/workspace`, not host paths, and it reads only its scoped credential set. The shared hop is `maybe_containerize` in `_cli.py`; the launch primitive is `cw.run_in_container`, whose `docker start -a -i` gives the container a real `-it` TTY — so interactive `call` renders its Textual UI inside the container just as a claude code session runs in a cw container. What the container runs is the shared bro-run description (top-level `bro_run.describe`, the same one summon children get): the `--host`-pinned inner command, the run bro's own `CW_BRO` (the calling session's ambient value is never forwarded — it would mis-theme the container's `cw banner`), and the bro git identity — every cw-launched session commits as bro, and a native bro run has no in-place session runner to export it — so the run's commits aren't attributed to the user's gitconfig identity and the container's master-push fence keys correctly.

The container's workspace clone bases on the host checkout's current `HEAD` — the entrypoint's default, the same launcher's-HEAD rule as `cw ss` workspaces and summoned children, so the bro sees the code the caller sees (committed state only; uncommitted changes never transfer). `--into <ref>` (on all three CLIs) bases it on any branch/tag/sha instead, resolved with an origin fetch when the ref isn't local; an unresolvable explicit ref fails fast. Host-side only like the grant/revoke flags below — it configures the clone, so it errors when the hop is skipped.

Inside a container the hop is impossible, so `ask` / `do-task` **relay** instead of running in-process: an invocation without `--host` runs as a summon of the named bro, getting the same scoped launch a host-side invocation gets, under the session's summon allow-list and depth cap (mechanism and flag rules — what rides the request, what errors — in `_cli.py:_relay_through_host` / `run`). `call` is interactive and summon is one-shot, so an in-container `call` still runs in-process, covered by the run-start credential gate (`bro/CLAUDE.md`).

`--host` runs the bro in the calling process — the debugging opt-out, and what the launch surfaces append to their own inner argv (the hop's container command; a summon child's `ask` argv) so the already-scoped inner run doesn't relay itself back. The scoped set is `bro_run.describe`'s (the bro-run surface of `cw.secrets.scoped_secrets`), so every surface that spawns a bro container computes it identically. Fast mode is the default, so the in-container bro is built via `bro.llm_spec.fast()` without any flag; `--slow` (available on all three) is forwarded into the container like `--rich` / `--text` to opt back out. `--effort LEVEL` (all three, choices from `cw.EFFORT_LEVELS`) overrides the spec's reasoning-effort knob via `LLMSpec.with_effort` and is forwarded the same way; no flag means the bro's own spec stands, and — the flag being an explicit ask, unlike implicit fast — a provider without the knob errors instead of falling back. `call` additionally decides TUI-vs-text on the host and forwards `--text` when the host terminal can't back the TUI (the container's PTY always reports a TTY).

`--grant-cred <secret>` / `--revoke-cred <secret>` (repeatable, on all three) adjust that scoped set before the hop via `credentials.apply_grant_revoke`: final set = `(computed | granted) - revoked`. They are host-side only (not threaded into the inner command), so `maybe_containerize` applies them when it hops and errors when it wouldn't (`--host` / already in-container — host runs are unscoped, so a revoke couldn't restrict anything). Strict: granting a secret already in the set, or revoking one absent from it, errors and stops; an unknown grant still fails loudly at hydration. The motivating case is running the emails e2e in a scoped container — `call --grant-cred gmail_creds --grant-cred google_api devoops "…"` keeps devoops scoped to +Gmail instead of forcing an unscoped `--host` run.

`--grant-summon <bro>` / `--revoke-summon <bro>` (repeatable, on all three) adjust the run's summon allow-list the same strict way: effective list = `(may_summon ∪ granted) − revoked` (`cw.summon_allow_list` over the run bro's MRO-collected `BaseBro.may_summon` defaults), with every name additionally validated against the bro registry so a typo fails at launch. The list is threaded through `cw.run_in_container` to the container's broker root — e.g. `call librorian --grant-summon devoops "…"` lets that librorian run summon devoops (librorian has no seed of its own). Host-side only like the credential pair — an in-process run has no broker root to enforce anything, so the flags error when the hop is skipped.

`--no-trails` turns recording off: `maybe_containerize` sets `TRAILS_DISABLED` in the container via `cw.run_in_container(extra_env=…)` (the in-container tracker factory then returns `NullTracker`) and drops `trails` from the scoped set. It acts only on the container hop, so it's mutually exclusive with `--host`; and unlike `--slow` / `--text` it isn't forwarded into the inner argv — the env var carries the effect in. The recovery use case (deploying `trails-server` through a bro) and the `--host` alternative (`TRAILS_DISABLED=1` in the shell) are in `trails/CLAUDE.md`.
