# bro/CLAUDE.md

Bro is the agent system: independent specialised agents (a "Bro") each run as a stateless LLM loop with their own system prompt and MCP-tool access. Conceptual model and rationale: `DESIGN.md`. Run any script with `--help` for flags.

## Layout

- `bro.py` — `BaseBro` ABC (the framework) and the framework helpers (`BroRaised`).

  Subclasses set `name`, `description`, and class-level `system_prompt = "..."` plus optionally `data_sources = [...]` and `mcp_servers = [...]`. An `mcp_servers` entry is a tool-pack module (`flow.mcp` — resolved through its conventional `spec` Toolset to the full roster, the preferred form), a bare `Toolset`, or an `llm.mcp.MCPServerSpec` from a scoping call (`flow.mcp.spec('add_task')`) — every form normalizes to the pure-metadata manifest (secrets + a `build()` factory) via `llm.mcp.as_spec` at collection. An entry — in `mcp_servers` and `data_sources` alike — may be wrapped with `base.condition.when(...)` to gate it on the assembling surface's facts, e.g. the dev toolset's `when(harness == 'bro', dev.mcp)` (claude has built-in file/shell tools). Entries are spelled by their qualified pack path (`flow.mcp`, `infra.mcp`, `dev.mcp`) so the definition reads standalone, without the import header; conditions are decided where composition happens (`llm.mcp.select`, harness `bro`), so an unmatched entry never mounts and its spec never builds (conditioning reference: `reference/conditions.md`). Live servers are built lazily, once, when the bro first runs tools (`_live_mcp_servers()`), so metadata surfaces (credential scoping, prompt composition, `bro show`) never construct them and a live server's constructor is free to hold real resources (flow's shared `System`).

  `BaseBro.__init__` walks the MRO from base to most-derived class and **concatenates each class's own `mcp_servers`, `data_sources`, and `system_prompt`** — so `class PPPDev(Dev): mcp_servers = [flow.mcp.spec()]` declares only what PPPDev *adds*; Dev's own `mcp_servers` entry (the dev MCP server) flows through automatically (same for the other two). The legacy `super().__init__(system_prompt=...)` escape hatch remains for callers that need a dynamic prompt computed at instantiation; no production bro currently uses it (a bro that wants the current time pulls it through the `CurrentTime()` data source instead).

  `BaseBro` also auto-prepends every `prompts/shared/*.md` to the system prompt and appends a `## Data sources` block describing each declared `DataSource`. When the bro has any namespaced tools or skills it also appends the tool-name rule (`prompts/tool_names.md`, templated on the `#wire` scheme). Each composed flavor renders once with its surface facts (`llm.mcp.render_text`: harness `bro`, the flavor's wire, the environment's credentials) — the wire is where the flavors diverge: `system_prompt` (bro-native LLM runs) renders `bare` (`namespace::tool` resolves to the wire name `namespace__tool` the bro's tool list carries), while `claude_system_prompt` (what `cw ss --bro` passes as claude's `--system-prompt`) renders `mcp`, because there each namespace is mounted as an MCP server and the wire names are `mcp__namespace__tool`. The bro's own class prompts (MRO-concatenated, before those additions) are kept as `persona`; `cw/system_prompt.py:_session_append_prompt` injects it into every cw-session (the `--persona` bro, ppp-dev by default) so it carries that bro's policies without running under `--bro`.

  **LLM spec.** `llm_spec` is a class-level attribute holding the bro's `LLMSpec` — a provider-specific frozen dataclass (e.g. `llm.llms.chat_gpt.LLMSpec` with typed `model`, `reasoning_effort`, `service_tier`) that carries the knobs the LLM accepts and validates them in `__post_init__`. Default is `chat_gpt.LLMSpec()` (gpt-5, no reasoning effort, no service tier); each bro overrides the whole spec at class level. Adding a new knob touches only the provider's spec, never `BaseBro`. Construction-time overrides go through `BaseBro.create(spec)` — it instantiates the class then replaces `llm_spec`, so subclass constructors never have to forward anything. Specs also expose `dump()` → dict / `LLMSpec.from_dict(data)` for serialization round-trip (used by `flow.process_inbox` to log the full spec into one DynamoDB column); `from_dict` eagerly imports the known providers so dispatch works in processes that haven't pulled the provider module in themselves.

  **Skills.** A bro can declare named procedures as markdown files under `<bro_pkg>/skills/*.md` with YAML frontmatter (`name`, `description`, body). `BaseBro.skills` walks `<pkg>/skills/` along the MRO and returns `{name: Path}`; derived classes override parents on name collision, parallel to `mcp_servers` / `system_prompt`. When skills are present, `__init__` auto-appends a `## Available skills` block to the system prompt and the service server mounts a `bro::skill(name)` tool whose body returns the skill's markdown body for the LLM to follow. A body is surface-templated: `{{iff #harness = bro}}…{{else}}…{{end}}` directives (`base.template`, via `llm.mcp.render_text`) fork a step between the bro-native LLM loop and the Claude Code harness, and `get_skill_body(name, harness=…, wire=…)` renders for its consumer — the `bro::skill` service tool is bro-harness-only (its mount is gated with `base.condition.when`; a `--bro` session runs `--bare` and works through the bro toolset, over `mcp` wire names), while a cw-session gets `claude`-rendered copies, so each surface sees only its own procedure. `skill_descriptions()` exposes the frontmatter programmatically for non-LLM consumers. Skill file format mirrors Claude Code's `SKILL.md` so the same file can be surfaced through both the bro framework and the Claude Code harness (a cw-session gets a rendered copy — see `.claude/CLAUDE.md`).

  **Run-start credential gate.** `run()` / `send()` (and the assistant server, which builds its own LLM per request) refuse to start when any name in `missing_secrets()` — the manifest plus the LLM key — doesn't resolve, listing all missing names: `run()` raises `BroRaised`, interactive surfaces reply with the report. The optional tier stays best-effort.

  **Interactive vs non-interactive paths.** Non-interactive runs (`bro.run()`, the `bro run` / `ask` / `do-task` CLIs) expose a built-in `raise` service tool — the agent calls it to abort with a reason when the request cannot be fulfilled (missing credentials, no appropriate tool, contradictory constraints, unclear/uninterpretable input); the call raises `BroRaised(reason)` out of `bro.run()`. `_system_prompt_for` pairs the note with the matching session-mode fragment (`prompts/autonomous_session.md` for non-interactive runs, `prompts/manual_session.md` for interactive ones — see `prompts/CLAUDE.md`), so the mode is injected at run start, never runtime-detected. Interactive paths (`bro.send()`, the HTTP server backing the iOS app, the `call` CLI) don't expose `raise` and inject a symmetric interactive-mode note instead — the agent is told to ask clarifying questions rather than guess, and to describe any blocker in its reply. Both service builds always mount a `banner` tool — the session environment facts of `cw banner --llm` rendered in-process (`cw.render_banner`, with the bro's name passed explicitly since bro-run containers drop `CW_BRO`), so every bro detects its environment without a shell; the playbook is `prompts/environment.md`. Both service builds also mount the summon tools when the process has a broker channel (`BROKER_CHANNEL` set), forwarding to the top-level `summon` module — a fresh channel client per call, every wait run off-loop via `asyncio.to_thread` so interactive surfaces stay responsive: `summon` blocks and relays the target's answer or failure (`detach: true` returns the request id right after the send instead), and `summon_check` checks on a request id — a non-consuming peek by default (`{state: pending|completed, …}`), `wait: true` to block and collect.

  **Observing.** Non-interactive runs stream a live trace of reasoning summaries, tool calls, tool outputs, and assistant text to stderr — timestamped plain log lines via `llm.observer.BoringRenderer` by default, or colored `rich` panels via `RichConsoleRenderer` when `--rich` is passed (`ask --rich`, `do-task --rich`, `bro run --rich`); both honor `observer=` on `BaseBro.run` for explicit overrides. Subclasses override `_make_observer()` to set the default observer; test bros return `NullObserver()` for silence.

  Assistant text flows through `on_assistant_message(text, terminal)` with the flag distinguishing mid-stream chatter (interim, model is still calling tools) from the terminal reply (also returned from `LLM.send`). `BoringRenderer` / `RichConsoleRenderer` render both — terminal as `reply` (bright), interim as `assistant`. Callers that already render the return value themselves (e.g. `do.call`'s `TextRenderer` / `TUIRenderer`) branch on `terminal=True` and skip to avoid double-emitting.

  **Credential manifest.** `bro.needed_secrets()` is the bro's component credential manifest — the union of each declared MCP server spec's and data source's `needed_secrets` (pure metadata — like flow's spec deriving its set from the named tools — so the manifest read never builds a live server) and the bro's MRO-collected `extra_secrets`. It is harness-aware: `needed_secrets(harness='claude')` counts only the components whose conditions hold on the claude harness — the set a cw-session hydrates, matching what `claude_persona_mcp_servers()` mounts (the claude-harness selection of declared servers + data sources plus the service server; the `bro:<name>` / `persona:<name>` split is `mcp_server.py`'s, consumed by cw — see `reference/cw.md`, "Session-local MCP serving"). It deliberately does **not** include the LLM key (`llm_spec.needed_secrets()`): surfaces that run the bro as an LLM process (`ask` / `do-task`) add it, but a claude-code session themed as the bro uses its own auth, not the bro's spec. Components declare what they read through the store (`flow.mcp.spec(...)` → `notion`, plus `focus` when it names the focus tools — derived from the named tools, so a scoped manifest over-declares nothing; `infra.mcp.spec(...)` → `infra, focus, aws`; `TMDb` → `tmdb`; `WebSearch` → `brave`; `chat_gpt.LLMSpec` → `openai`); `extra_secrets` is the class-level escape hatch for environment needs no component expresses (ppp-dev → `github`, devoops → `aws`), MRO-walked and unioned exactly like `mcp_servers`. The host hydrates the per-surface set (manifest + LLM key and/or session baselines) into a scoped per-container credential store before the container starts — `cw.run_in_container` + `credentials.build_scoped_store` (`docker cp`'d into the container, no host-side store); required hydration is strict (a missing secret fails loudly on the host). Full flow, including the per-surface set breakdown, in `reference/cw.md` ("Scoped credential hydration"). `bro show` renders the manifest, the optional tier, the LLM key on its own line, and a note that the session baselines are added per-surface.

  **Optional credential tier.** `bro.optional_secrets()` is the best-effort sibling of the manifest — the union of each declared component's `optional_secrets` minus `needed_secrets()` (a hard requirement is never downgraded). It is for credentials a component uses *if present* but degrades without, e.g. the LLM key behind a `SearchableDataSource`'s query-focused fetch summary. The host hydrates it via `build_scoped_store(optional=...)`: resolvable names are materialised, unresolvable/unknown ones skipped — so an absent optional secret degrades the component instead of failing container launch (like `needed_secrets`, harness-aware — each cw surface adds the tier of the components it mounts). `base.credentials.available(name)` is the non-raising presence predicate that powers both the runtime gate and the credential description directives: `{{iff #creds contains <name>}}…{{else}}…{{end}}` templating (`base.template`, via `llm.mcp.render_text`) in a component's static description strings, rendered against live availability at the assembling layer (`_NamespacedTool` for tool descriptions, `_render_data_sources` / `bro show` for data-source summaries), with the component's declared secrets as `#creds`' universe — testing an undeclared name raises. Separately, `needs_docker` (a plain class attribute, default `False`; only `Devoops` sets it `True`) declares whether the bro does docker work (building/pushing images for deploys); the host grants the docker socket to a `--bro`/`ask` container only when it's set — claude code sessions get it unconditionally.

  **Usage publishing.** `_create_llm` passes `agent=bro.agent` (the `bro//<name>` surface identity), so the provider publishes its cumulative per-model usage under that identity to the env-pointed usage file (root `usage` module) after every LLM call. Tool subprocesses inherit the pointer, which is how `setup/claude_commit_footer.py` credits a native bro run's commits — the file carries the agent identity itself because bro-run containers drop `CW_BRO`.

  **Recording.** Sibling of the observer path: each `BaseBro.run()` / `.send()` also opens a *trail* via an `llm.tracker.Tracker` and emits framework bookend steps (`start_trail` → auto `system_prompt` step, `end_trail` → `end` step with the run's `end_reason`). The same `Tracker` is plumbed into the LLM (parallel to `observer`) so the provider implementation can emit the in-between steps directly (`user_input`, `llm_call` with raw request+response payload + token counts, `reasoning`, `assistant` with `terminal` flag, `tool_call`, `tool_result` with `is_error`). Default factory builds an `HTTPTracker` from the `trails` secret; recording is mandatory in production — a missing config raises rather than silently falling back. `NullTracker` is opt-in: env-var kill switch via `TRAILS_DISABLED` (presence-checked, any value; checked before the config check, so it works even with a missing config or a down server), per-run via `tracker=NullTracker()` on `.run()` / `.send()`, process-wide via `bro.bro.set_default_tracker_factory(NullTracker)` (what `conftest.py` does for tests). The env var governs only the default factory — an explicit per-run `tracker=` and a custom `set_default_tracker_factory(...)` still win. `BaseBro._make_tracker()` is the per-bro hook. Trail schema and lifecycle live in `llm.tracker` and the framework revision is recorded as `configs.VERSION` on each trail header. The read side — deployed `trails-server`, reader library, `trails` CLI, schema-evolution rules — is `trails/CLAUDE.md`.
- `channel.py` — `BroChannel`, the bro-side broker consumer: a thin adapter over `broker.client.Client` emitting the run lifecycle to the host dispatcher. `BaseBro.run()` builds one via the `_make_channel()` hook (`BroChannel.from_env()` — `None` when `BROKER_CHANNEL` is unset or the broker package is unimportable; the broker imports are deferred to call time, so importing `bro` never requires broker) and emits `started{trail_id}` right after `start_trail` and `completed{result, end_reason}` after `end_trail`, with `result` defined per end reason (terminal → the run's return value, raised → `BroRaised.reason`, error → the exception string). Fires only for `BaseBro.run` (LLM-process children): interactive `send()` emits nothing, and a claude-code `--bro` session never calls `run()`. `close()` confirms delivery (`ClientTransport.close(confirm=True)`) — the lifecycle terminal is typically the process's last act before exit. `conftest.py` drops `BROKER_CHANNEL` so tests never emit into a live session channel.
- `bros/` — one package per concrete agent (`bros/<name>/__init__.py`); `bros/__init__.py` declares the `BRO_SPECS` map (`name -> "module:ClassName"`) the registry loads lazily.

  `bros/bro/` defines the concrete `Bro(BaseBro)` — the "default bro" registered as `bro`, with a minimal go-to system prompt and no MCP servers. **All other bros inherit from this `Bro`** (not `BaseBro` directly), so they pick up the shared defaults via the MRO walk; inherit from `BaseBro` only when you want to opt out of those defaults. It owns the shared `/ask` skill (`bros/bro/skills/ask.md`) — the summon UX every bro inherits: phrasing → target + self-contained prompt, client pick (`summon` CLI vs the `summon` service tool), foreground-vs-background, failure relay. Protocol and enforcement live in the `summon` module and `cw/summon.py`, not in the skill.

  Specialists:
  - `assistant/` — chat + flow tools
  - `pm/` — Flow inbox triage
  - `librorian/` — steward of the Flow media library (adds, maintains, recommends)
  - `devoops/` — autonomous operations: deploys, restarts, and infra inspection. Primitives are the MCP tools in `infra/mcp.py` (mounted as the `infra.mcp` pack), plus the dev bro's `bash` tool for ad-hoc shell work and a task-scoped `flow.mcp.spec(...)` (read/write tasks + log to task pages, for pulling deploy context and recording outcomes); per-workflow procedure lives in `bro/bros/devoops/skills/*.md` (currently `deploy.md`) and is loaded on demand via the `skill` service tool
  - `dev/` — generic developer with file/shell/search tools from sibling `mcp.py` (`bash` and `grep` shell out, file ops are thin Python; `spec` is the dev `Toolset`, tools registered via `@spec.tool` — same shape as flow's / infra's; see sibling `REFERENCE.md` for the shared output cap / skipped-content markers / fat-finger clamp / background-job model the LLM fetches via `read_reference`; the windowing implementation behind that policy is `base/text_window.py`), plus background jobs — `job` / `watch` / `kill` for processes that outlive a `bash` call's timeout, the bro-side analog of Claude Code's `run_in_background` + `TaskOutput` / `TaskStop` (process machinery — spool, cursor, watch lock, atexit group-kill — in sibling `jobs.py`, held as the `Toolset` state); owns the `/audit` skill (`bro/bros/dev/skills/audit.md`), a read-only codebase-audit playbook inherited by every dev-derived bro
  - `ppp_dev/` — PPP-specific developer: inherits `dev/` (and its `/audit` skill), adds the flow toolset and its own `/fix`, `/pr`, `/land` skills (in `bro/bros/ppp_dev/skills/`; task-driven workflow); `dive-in` seeds `/fix` as its first user message
- `datasources/` — `DataSource` ABC + `SourceUnavailable` (`base.py`) + connectors to read-only sources. The base ABC declares `name`, `summary`, `namespace` (a property, `f'{name}-source'`), `needed_secrets` / `optional_secrets`, and `as_mcp_server()`. The `SearchableDataSource` subclass (`searchable.py`) adds the canonical `search` + `fetch` pair, exposed as bare `search` / `fetch` tools inside the source's `<name>-source` namespace (wire name `<name>-source__search`). Subclasses implement `search` and `_fetch_content(id)` (raw record); the base `fetch(id, query=None)` returns the raw record when no query is given and otherwise summarises it for the query via `mu` (one `source_summary` prompt for every source). That summary path reads the LLM key, so `SUMMARY_SECRET='openai'` is a base-level `optional_secret` (best-effort, hydrated when present); with it absent, a non-null `query` raises rather than silently returning raw text. The fetch tool's description advertises which mode is live via a credential directive (see `llm/mcp.py`). Subclass `DataSource` directly for sources that don't fit the search/fetch shape and override `as_mcp_server()`, stamping `self.namespace` onto the returned server. Currently:
  - `http.py` — shared HTTP transport for the sources (`get_json` / `get_text`): throwaway per-request sessions with a tight timeout and the common User-Agent
  - `wikipedia.py` — Wikipedia REST API; `_fetch_content` returns the article extract (base layers the query summary)
  - `tmdb.py` — movies + series; needs the `tmdb` secret
  - `open_library.py` — books, no auth
  - `web_search.py` — Brave Search; needs the `brave` secret
  - `current_time.py` — current local date and time; single `get_time` tool (wire `current-time-source__get_time`)
  - `references.py` — ready-made `FileSource` instances over the repo's canonical reference docs (`environment` → `prompts/environment.md`, `template` → `reference/template.md`, `conditions` → `reference/conditions.md`); a bro mounts one by listing it in `data_sources` (PPPDev mounts all three)
  - `file.py` — `FileSource(name, summary, path, render=True)`: surface a static reference file as a single `read` tool (wire `<name>-source__read`) whose description carries the summary. One rendering is read by every harness, so the body must be surface-neutral — `read` renders with no facts and a `#harness` directive raises; `render=False` serves the file verbatim, for a doc whose payload is the directive syntax itself. Use for canonical docs the bro consults on demand; the ready-made instances live in `references.py`
- `registry.py` — process-wide registry of bro classes: `register(cls)`, `get_class(name)`, `create_bro(name, llm_spec=None)`, `list_classes()`. `create_bro` returns a fresh instance every call. Lookup is lazy: a miss imports only the one bro module named in `BRO_SPECS`, so `create_bro('pm')` never pulls in another bro's dependency graph (librorian's trafilatura/dateparser, devoops's boto3, …); only `list_classes()` (i.e. `bro list`) imports them all. Tests flip the module-level `_autoload` off to isolate the registry to hand-registered bros
- `fork.py` — fork of a recorded trail. `replay_messages(trail, up_to_step_id)` rebuilds the OpenAI input list from a `RecordedTrail`'s steps (system + user messages + each `llm_call.response.output` items — sanitized for input reuse: response-only `status` and null-valued optionals stripped — + `function_call_output`s from `tool_result`s). `fork(parent_trail, up_to_step_id, *, llm_spec=None, system_prompt=None, record=True, tracker=None)` returns a fresh `Bro` preseeded with the parent's prefix and a new trail bearing `parent=Parent(trail_id, step_id, 'fork')`; the caller drives it with `.send(next_message)`. The replay path is picked automatically: same-provider + same-model + fork at an `llm_call` step + no `system_prompt` override → server-side via `previous_response_id` (the new LLM gets `_last_response_id` seeded from the fork step; OpenAI carries the cached prefix). Anything else → client-side message replay via `_input_prefix`.
- `run.py` (`bro`) — CLI: `bro run <name> <input>`, `bro list`, `bro show <name> [--system-prompt]` (markdown info card; renderer in `show.py`)
- `server/server.py` (`bro.server.server`) — aiohttp wrapper exposing the `assistant` bro on `POST /v1/chat/completions` (OpenAI-compatible). Used by the iOS app
- `app/ios/` — iOS chat client; see `app/ios/CLAUDE.md`

## PM Bro

`bros/pm/` is the single source of truth for Flow inbox triage policy — status taxonomy, importance/driver semantics, every per-kind policy (payment receipts, subscription renewals, bill payments, media items, title metadata extraction, sphere tags, …). Its `SYSTEM_PROMPT` is canonical: do not duplicate the policies elsewhere. Two delivery surfaces consume it:

- `process-inbox` TUI (`flow/process_inbox.py`) — Textual app; instantiates `PM()` with no MCP servers and constrains it to a JSON suggestion protocol so the user previews every change before it applies. Engine details in `flow/process_inbox.REFERENCE.md`
- `cw ss --bro pm` — Claude Code session with PM's system prompt and the flow MCP toolkit; PM calls `update_task` / `add_task` itself (no preview). Use when you want to triage from a chat UI rather than the TUI

Changes to triage policy go in `bro/bros/pm/__init__.py` and propagate to both surfaces on next process start.

PM also owns the `/feature` skill (`bro/bros/pm/skills/feature.md`) — a coordinator playbook for driving a complex feature across many `dive-in` sub-sessions (design → review → plan → per-stage implement → integrate → deploy → verify → close). The root runs as `cw ss --bro pm` and does no hard work itself: it owns the feature task page (the single source of truth) and hands the user one `dive-in` command per phase. Stages PR into a per-feature integration branch (`/pr --base <branch>`) and integrate to master once at the end; see the skill body for the per-phase commands. It's orthogonal to triage — the `process-inbox` TUI mounts no `skill` tool, so the skill is inert there (it only adds a one-line entry to PM's `## Available skills` block).

## Adding a Bro

Create `bros/<name>/__init__.py` with `from bro.bros.bro import Bro` and a `class YourBro(Bro)` (inherit from the concrete `Bro` so you pick up the shared defaults; use `BaseBro` only when you want to opt out). Declare `name`, `description`, and `system_prompt` as class attributes; add tool sources as class attributes too:

- `system_prompt = "..."` — class-level. When you `class B(A)` and both declare `system_prompt`, `__init__` concatenates A's then B's (MRO base-to-derived) so subclasses only declare their *additions*.
- `data_sources = [YourSource()]` for read-only data connectors
- `mcp_servers = [flow.mcp]` for the full flow toolset (a tool-pack module stands for its full roster)
- `mcp_servers = [flow.mcp.spec('add_task', 'list_tasks')]` to scope to specific tools (validated at declaration)
- `mcp_servers = [infra.mcp]` for the devops toolset; scope with `infra.mcp.spec(...)`
- `mcp_servers = [when(harness == 'bro', dev.mcp)]` (`from bro.bros import dev`) for the developer toolset (file/shell/search tools; roster in `bro/bros/dev/mcp.py`), gated off the claude harness as in `Dev`'s own declaration; scope to specific tools with `dev.mcp.spec('bash', ...)`
- Roster-based servers are declared as an `llm.mcp.Toolset` in their module — tools register via `@spec.tool`, secrets via the static `secrets` class var or a `get_secrets` override when the set depends on the selected tools (flow); `MCPServerSpec.of(ServerClass, *ctor_args)` is the manifest escape hatch for irregular server classes
- `mcp_servers` and `data_sources` are also walked along the MRO and concatenated — `PPPDev(Dev)` with `mcp_servers = [flow.mcp.spec()]` ends up with Dev's dev MCP server *plus* the flow toolset.
- An entry in either list may be gated on surface facts: `mcp_servers = [when(harness == 'bro', spec)]` (`from base.condition import when`, `from llm.mcp import harness`; `when` also accepts a plain bool for a genuinely static predicate) — or choose among alternatives with `iff(c1, a1, c2, a2[, e])`, which raises when nothing matches and no else item is given. Conditions evaluate at assembly, so an unmatched entry never mounts and its spec never builds — see `reference/conditions.md`. Declarations skip the `ClassVar` annotation — BaseBro's class-level declarations carry the types; ruff's RUF012 is ignored for `bro/bros/*/__init__.py`.
- `llm_spec = chat_gpt.LLMSpec(...)` (or any other provider's `LLMSpec`) overrides the LLM recipe. Per-instance overrides go through `YourBro.create(spec)`.
- `extra_secrets = ('github',)` declares credentials no component expresses (a bro's environment needs). MRO-walked and unioned like `mcp_servers`; folded into `bro.needed_secrets()`, which the host hydrates into the scoped container store. Most secrets come from the declared MCP servers / data sources / `llm_spec` and need no entry here — see "Credential manifest" above.
- `may_summon = ('devoops',)` declares which bros this bro may summon — its static outgoing allow-list. A root session running as the bro gets it adjusted per session by the launchers' `--grant-summon`/`--revoke-summon` flags; when the bro runs as a summoned child, the seeds are its entire list (grants stay a root-session surface), so summons chain transitively through seeded bros, bounded by the host's depth cap (the effective-list computation and enforcement live in `cw/summon.py`). MRO-walked and unioned like `extra_secrets`. Currently ppp-dev and pm seed it; grow by precedent — every seed is an opt-in blast radius, transitively.
- Drop markdown files into `bros/<name>/skills/*.md` (YAML frontmatter `name`, `description`; markdown body after the closing `---`) to declare skills the LLM can invoke via the `skill` service tool. Filename stem is the canonical name; the `name:` frontmatter is validated against it at load and a mismatch raises `ValueError`. The frontmatter `description:` is paragraph-length (Claude Code reads it for slash-command discovery); the bro system-prompt listing truncates it at the first sentence so the prompt doesn't bloat — write the trigger sentence first. Skills follow the same MRO walk as `system_prompt` and `mcp_servers`: each ancestor's `skills/*.md` files contribute, but because skills are keyed by name (not concatenated), derived classes override parents on name collision (`ppp_dev/skills/fix.md` would shadow a `dev/skills/fix.md` of the same name). Anything dropped into `bros/bro/skills/` becomes available to every bro by default — the shared-skill mechanism (`/ask` is the precedent).

**Register the new bro manually** — add one entry to `BRO_SPECS` in `bros/__init__.py` (`'your-name': 'bro.bros.your_pkg:YourBro'`). There is no auto-discovery; the map entry is required for `create_bro('your-name')` to work. The key must equal the class's `name` attribute — the registry validates this when it lazily imports the module, and the map itself carries no imports, so adding a bro never slows startup for the others.

## Adding a DataSource

Set `name` (slug) and `summary` (one-line; injected into the system prompt of every Bro that uses it). For the common search/fetch shape, subclass `SearchableDataSource` and implement `async search(query, limit) -> list[Hit]` and `async _fetch_content(id) -> str` (the raw record). The base provides `fetch(id, query=None)`: it returns the raw record when no query is given and otherwise summarises it for the query via `mu` — so you don't write summarisation per source. That summary path depends on the `openai` key, declared once on the base as an `optional_secret`; with the key absent a non-null `query` raises (no raw-text fallback). For other shapes (e.g. a singleton fact like `current_time.py`), subclass `DataSource` directly and override `as_mcp_server()` to expose whatever tools fit. When an upstream HTTP/network failure makes the source temporarily unusable, raise `bro.datasources.base.SourceUnavailable(source, reason)` rather than letting raw transport exceptions escape — the agent loop turns it into a tool result the model can route around. If the source reads a credential through the store, declare it with `needed_secrets = ('tmdb',)` (or `optional_secrets` for one it degrades without) so the host hydrates it into any bro that uses the source (see "Credential manifest"). Bind to a Bro by declaring `data_sources = [YourSource()]` on its class.
